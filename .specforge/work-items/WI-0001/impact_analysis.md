| 维度 | 评估 |

| 模块 | 对应文档章节 | 优先级 | 复杂度 |

## 3. 关键风险点（必须在 design 阶段解决）

### 3.1 架构风险（高）
1. **安卓端离线同步**：这是整个项目最复杂的子模块。涉及本地 SQLite、增量游标（server_seq）、幂等推送（client_uuid）、冲突检测、照片分片上传、弱网重试。文档 §59-62、§107.4 已定义原则但无实现细节，design 阶段必须产出完整同步协议。
2. **三层状态联动一致性**：`DailyReport.status` / `DailyReportIssue.status` / `issue_quality_status`（文档 §102.3）三层状态任一层变更要联动其他层，是高频 bug 源。design 阶段必须为每一对联动写明确触发规则和测试用例。
3. **报告版本与快照管理**：报告变更通过复制生成新版本（文档 §23、§102.5），涉及 root_report_id / previous_report_id / report_version / is_current_effective 协同。design 阶段必须画出完整版本树状态图。

### 3.2 技术选型风险（中，需在 design 阶段冻结）
1. **安卓离线数据库**：WatermelonDB vs react-native-sqlite-storage vs 其他。未定则安卓端无法编码。
2. **照片存储方案**：本地磁盘的目录规划、压缩参数（文档 §103.4 建议长边 1600-1920px、质量 75-85、≤1MB）、哈希策略、原图保留策略。
3. **报告导出引擎**：poi-tl 的模板设计、图片占位符渲染、发布固化时文件不可覆盖的实现。
4. **认证方案**：JWT vs Session、安卓端 token 刷新与离线鉴权、本地数据加密。

### 3.3 资源风险（中）
1. **服务器内存 3.6GB 偏紧**：Java + PG + Nginx 同机。design 阶段需给出 JVM/PG 内存调优参数。
2. **磁盘 23GB 对照片是瓶颈**：design 阶段需规划照片清理/归档策略。

### 3.4 业务文档遗留问题（低，design 阶段澄清）
1. `confirmed_at` / `locked_at` 字段语义（intake 已识别）
2. 项目问题池"后续更正"是否终态
3. 照片质量检测 V1 能力边界（模糊/过暗）
4. 标准推荐 V1 实施范围
5. 接口契约、API 规范、错误码体系（文档未覆盖）
6. 章节号不连续（缺 20/22/24/26/30/37/42/77/89/99）

## 4. 依赖关系

### 4.1 外部依赖
- 无第三方 SaaS 依赖（通知仅 App 内，无企微/钉钉/短信）
- 无外部标准库数据源（标准库由管理员手工维护）

### 4.2 内部模块依赖（决定实施顺序）
```
阶段1（基础/权限） ← 阶段2（项目/检查表） ← 阶段3（任务/安卓）
                                              ↓
阶段7（审批/发布） ← 阶段6（报告/快照） ← 阶段5（确认/复核） ← 阶段4（日报/问题池）
```
阶段 1-2 是基础，必须先完成；阶段 3-7 是主链，严格按顺序。

## 5. workflow_path 选择

基于影响分析结果：

- 变更类型为全新产品构建
- 涉及完整的 需求 → 设计 → 任务拆解 → 实施 链路
- 业务复杂度高（20+ 表、4 套状态机、双端、离线）
- 不符合 code_only_fast_path 的条件（不是单文件小改）

**推荐 workflow_path**：`requirement_change_path`（已在 WI 创建时确定）
**workflow_type**：`feature_spec`（已在 WI 创建时确定）

## 6. 建议拆解粒度

由于业务文档极其详尽（9192 行），建议 requirements 阶段按以下粒度拆解：
- 按 MVP 阶段（1-7）拆为 7 个需求域
- 每个需求域内按核心对象（Project / Organization / DailyReport / Report 等）拆为子需求
- 验收标准严格对应文档 §103.2 性能 SLA 和 §105.1 MVP 验收标准
