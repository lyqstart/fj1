# 飞检现场管理系统 — Intake

## 1. 项目概述

构建一个**独立产品**：「飞检现场管理系统」。用于第三方飞检公司进行现场检查管理，覆盖项目建立、项目检查表编制、检查任务派发、现场检查、日报形成、项目问题池沉淀、周报/月报生成、审核发布等流程。

本系统的唯一业务输入为 `doc/飞检现场管理系统_业务逻辑定稿_v1.14_最终干净版_开发输入.md`（9192 行，业务侧已定稿），所有业务术语、状态机、字段基线、页面职责、MVP 切分均以该文档为准。

## 2. 用户群体与使用规模

- **使用群体**：第三方飞检公司内部使用（企业内部系统）
- **用户规模**：20-50 名用户，10-20 人同时在线
- **数据量基线**（文档 §103.2）：单项目 500 任务 / 3000 问题 / 10000 照片 / 200 报告
- **不是**对外发布的公开产品，**不**做甲方外部账号门户（V1 默认只支持系统内项目成员按权限查看）

## 3. 性能与并发要求

- 普通列表查询 P95 ≤ 800ms
- 详情页查询 P95 ≤ 600ms
- 日报文本提交 P95 ≤ 2s（照片异步上传）
- 审批通过/退回 P95 ≤ 1s
- 报告草稿预览导出（100 问题 / 300 照片）≤ 60s
- 发布固化导出（100 问题 / 300 照片）≤ 120s，失败不得改变报告状态
- 安卓单设备照片并发上传 2-3 个，失败重试

## 4. 可用性

- **级别**：需要较高可用（99.9%+），商业服务标准
- **项目特性**：非长期运行项目，"能稳定运行能完整跑通项目即可"，但运行期间不能频繁故障

## 5. 关键约束（强制）

### 5.1 必须支持离线（P0）
现场部分区域**没有 4G 或 WiFi**，安卓端必须支持完整的离线作业能力：
- 现场拍照、写描述、选责任单位、选位置、保存问题、提交日报全部可离线进行
- 先本地保存，再异步同步
- 文本和照片分开同步，失败可重试
- 离线时使用本地缓存的标准库做轻量标准推荐
- 通知在离线时收不到，用户联网后批量拉取未收到的通知

### 5.2 双端都要做（P0）
- **Web 端**（PC）：任务派发、日报确认、问题池、报告生产、审批发布、配置管理、管理统计
- **安卓端**（现场）：现场检查、问题取证、问题保存、提交日报、退回修改
- MVP 范围（文档 §105.1 阶段 1-7）全部完成，不因团队规模压缩

### 5.3 通知机制（P0 共识）
- **仅 App 内通知**（站内消息 + 待办列表红点）
- **不做**外部推送、短信、邮件、企业微信/钉钉
- 离线时通知随同步批量拉取
- 重大问题电话通知**仅系统内留痕**（`MajorIssueNotificationRecord`）

### 5.4 安全合规
- 无特殊行业合规要求（无等保/数据出境/个保法等额外约束）
- 按文档 §103.3 基线：HTTPS、密码哈希、项目级 RBAC、文件鉴权访问、越权留痕
- V1 认证方式：账号密码登录；SSO/手机验证码为可选项

## 6. 重大业务裁决（P0 共识，覆盖文档原表述）

以下三项裁决在与用户的多轮澄清中确认，**优先于文档原文**：

### 6.1 重大问题整改期限（覆盖文档 §17.2 / §101.10）
文档原表述"重大 = 立即整改"无法落库（`rectification_deadline` 是日期字段）。

**最终规则**：
- 默认：重大等级 `rectification_deadline = confirmed_at 当日 23:59:59`（即"当日内"）
- 项目可通过配置项 `major_issue_deadline_hours` 覆盖为 N 小时
- `rectification_deadline` 字段**始终非空**，类型 `DateTime`（精确到秒）

整改期限完整规则：
```
一般  → confirmed_at + 7 天
较大  → confirmed_at + 3 天
重大  → confirmed_at 当日 23:59:59（或项目配置 N 小时）
```

### 6.2 MVP 范围
维持文档 §105.1 定义的阶段 1-7，不进一步收敛：
```
阶段 1：基础数据与权限骨架
阶段 2：项目配置与检查表
阶段 3：检查任务与安卓离线骨架
阶段 4：日报提交与项目问题池生成
阶段 5：日报确认与问题复核
阶段 6：报告生产与问题快照
阶段 7：审批、发布、导出固化
```
报告变更、统计看板、标准推荐优化进入 V1.1（阶段 8-9）。

### 6.3 通知机制
见 5.3。

### 8.1 服务器资源风险（design 阶段必须处理）
- **内存 3.6GB 偏紧**：Java + PG + Nginx 同机，JVM 堆需限制在 1G 以下，PG shared_buffers 限 512MB。如后期 OOM，考虑扩容到 8G（不换语言，Java 调优后可跑）。
- **磁盘 23G 对照片是瓶颈**：10000 张 × 1MB = 10G/项目，多项目需规划清理策略或独立数据盘。

## 9. 待 design 阶段解决的事项

以下事项不阻塞 intake，由 sf-design 在设计文档中给出方案：
1. 安卓离线数据库技术选型（WatermelonDB / react-native-sqlite-storage / 其他）
2. 照片压缩与本地存储方案（目录规划、压缩参数、哈希策略）
3. 报告导出引擎的具体实现（poi-tl 模板设计、快照渲染）
4. 认证方案（账号体系、token 方案 JWT/Session、安卓端 token 刷新与离线鉴权、本地数据加密）
5. 接口契约规范（REST 风格、分页、错误码、同步协议）
6. PG 升级方案（备份 → 卸载 13 → 安装 16 → 恢复）
7. confirmed_at/locked_at 字段语义（确认动作时间 vs 锁定持久化时间）
8. 项目问题池"后续更正"是否终态
9. 照片质量检测 V1 能力边界（模糊/过暗是否做）
10. 标准推荐 V1 实施范围（是否进 MVP）
11. 三层状态联动一致性策略
