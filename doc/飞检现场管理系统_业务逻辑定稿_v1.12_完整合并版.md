# 飞检现场管理系统业务逻辑定稿 v1.7

> 本文件用于固化当前已经确认的业务逻辑结论，作为后续继续讨论、需求设计、原型设计、数据库设计和开发实现的依据。
>
> 本文件不是原始讨论纪要，而是将已确认内容整理成可执行的业务规则。

---

## 1. 总体定位

本系统用于第三方飞检公司进行现场检查管理，覆盖项目建立、项目检查表编制、检查任务派发、现场检查、日报形成、问题台账沉淀、周报/月报生成、审核发布等流程。

V1 版本做到：

```text
项目 → 项目检查表 → 检查任务 → 现场检查 → 日报 → 问题台账 → 周报/月报 → 审核 → 发布
```

V1 版本不做整改闭环、不做独立归档模块，但必须为后续整改闭环预留数据基础。

---

## 2. 核心业务主链

系统核心主链固定为：

```text
项目
  ↓
项目检查表
  ↓
检查任务
  ↓
现场检查
  ↓
日报
  ↓
问题台账
  ↓
周报/月报草稿
  ↓
报告问题快照
  ↓
组长复核
  ↓
报告审核人审核
  ↓
发布
  ↓
V1 结束
```

最核心的数据来源规则固定为：

```text
日报 → 问题台账 → 周报/月报
```

即：

1. 问题台账的唯一来源是日报。
2. 周报、月报的唯一问题来源是问题台账。
3. 周报、月报不能直接新增问题。
4. 周报、月报不能直接引用现场检查记录中的问题。
5. 周报、月报不能直接引用日报草稿中的问题。

## 3. 项目 Project

### 3.1 项目的业务含义

项目是系统业务源头。

项目来自公司与甲方签订的合同。合同中会约定甲方单位、检查站场、检查范围、检查专业、检查内容、交付成果等。

V1 系统不管理合同本身，但项目需要承接合同中与检查业务有关的基本信息。

### 3.2 项目的创建方式

项目可以提前单独创建。

后续创建项目检查表、检查任务、日报、周报、月报时，均选择所属项目。

### 3.3 项目建议字段

| 字段 | 说明 |
|---|---|
| 项目名称 | 必填 |
| 项目编号 | 可手动填写或系统生成 |
| 甲方单位 | 必填 |
| 检查范围 | 简要描述 |
| 检查专业 | 可多选 |
| 项目负责人/组长 | 必填 |
| 项目状态 | 进行中 / 已结束 |
| 创建人 | 系统记录 |
| 创建时间 | 系统记录 |

### 3.4 项目业务规则

1. 项目是检查表、检查任务、日报、问题台账、周报、月报的归属容器。
2. 一个项目可以有多份项目检查表。
3. 一个项目可以有多个检查任务。
4. 一个项目可以有多份日报、周报、月报。
5. 周报/月报属于项目，不只属于某个检查员个人。

## 4. 项目检查表 Project Inspection Form

### 4.1 检查表的业务含义

V1 中，检查表不优先理解为全局可复用模板，而应理解为：

> 组长根据某个项目的检查要求整理出的项目专用检查表。

检查表属于项目。

一个项目可以有多份项目检查表，因为不同专业可能需要不同检查表。

例如：

```text
某飞检项目
  ├── 防腐专业检查表
  ├── 土建专业检查表
  ├── 无损检测检查表
  └── HSE 检查表
```

### 4.2 与“模板”的关系

V1 不把检查表设计成全局模板系统。

可以支持“从历史检查表复制”来提高录入效率，但复制后的检查表仍然属于当前项目。

### 4.3 项目检查表建议字段

| 字段 | 说明 |
|---|---|
| 所属项目 | 必填 |
| 检查表名称 | 必填 |
| 专业 | 防腐 / 土建 / 无损检测 / HSE 等 |
| 编制人 | 组长 |
| 状态 | 草稿 / 已发布 / 已停用 |
| 检查项列表 | 组长整理的检查内容 |
| 创建时间 | 系统记录 |

### 4.4 检查项建议字段

| 字段 | 说明 |
|---|---|
| 所属检查表 | 必填 |
| 序号 | 检查项排序 |
| 检查内容 | 检查员需要检查的内容 |
| 专业 | 可继承检查表专业 |
| 分类 | 可选 |
| 判定依据 | 可选 |
| 默认整改建议 | 可选 |

### 4.5 项目检查表业务规则

1. 项目检查表由组长编制。
2. 项目检查表属于项目。
3. 一个项目可以有多份项目检查表。
4. 项目检查表发布后，才能派发给检查员执行。
5. 检查员不能修改项目检查表。
6. 检查员现场发现表外问题时，是新增“表外问题”，不是修改检查表。

---

## 5. 检查任务 Inspection Task

### 5.1 检查任务的业务含义

检查任务是组长将项目检查表派发给检查员执行的任务。

检查任务回答：

```text
谁，在什么时候，拿哪张项目检查表，去哪个现场检查。
```

### 5.2 检查任务建议字段

| 字段 | 说明 |
|---|---|
| 所属项目 | 必填 |
| 项目检查表 | 必填 |
| 检查员 | 必填 |
| 计划检查日期 | 可选 |
| 计划检查地点 | 可选 |
| 任务状态 | 待执行 / 执行中 / 已提交 / 已退回 / 已完成 |
| 创建人 | 组长 |
| 创建时间 | 系统记录 |

### 5.3 检查任务业务规则

1. 组长创建检查任务。
2. 一个项目检查表可以派发给一个或多个检查员。
3. 一个检查员可以执行多个检查任务。
4. 检查任务创建时，不强制填写详细被检查单位。
5. 被检查单位的详细信息由检查员到现场后填写。
6. 检查员在移动端看到自己的检查任务。
7. 检查员从检查任务进入现场检查。

---

## 6. 实际受检单位 Inspected Party

### 6.1 业务含义

被检查单位的详细信息通常只有检查员到现场后才知道。

因此，组长派发任务时不强制完整填写施工单位、监理单位、检测单位等详细信息。

检查员现场填写实际受检单位。

### 6.2 受检单位类型

| 类型 | 示例 |
|---|---|
| 施工单位 | 现场施工承包商 |
| 监理单位 | 工程监理单位 |
| 检测单位 | 无损检测等检测单位 |
| 作业区/属地单位 | 现场属地管理单位 |
| 其他 | 现场实际出现的其他责任主体 |

### 6.3 业务规则

1. 检查员到现场后填写实际受检单位。
2. 一个检查任务/日报可以关联多个实际受检单位。
3. 每条问题必须选择责任单位。
4. 责任单位来自本次日报中填写的实际受检单位列表。
5. 责任单位需要保存名称快照，避免后续单位名称变化影响历史记录。

---

## 7. 现场检查与问题

### 7.1 现场检查

检查员执行检查任务时，按照项目检查表逐项检查。

每个检查项可以形成检查结果。

检查结果建议状态：

| 状态 | 含义 |
|---|---|
| 待检查 | 初始状态 |
| 合格 | 已检查，无问题 |
| 有问题 | 已检查，发现问题 |
| 不适用 | 本次现场不涉及 |
| 未检查 | 应检查但未检查，需要说明原因 |

### 7.2 表内问题与表外问题

现场问题分为两类：

| 类型 | 含义 |
|---|---|
| 表内问题 | 来源于项目检查表中的某个检查项 |
| 表外问题 | 现场发现但不在项目检查表中的问题 |

### 7.3 表外问题业务规则

1. 检查员可以新增表外问题。
2. 新增表外问题不是修改项目检查表。
3. 表外问题可以进入日报。
4. 表外问题可以进入问题台账。
5. 表外问题可以被周报/月报引用。
6. 表外问题应保留“是否建议加入检查表”的扩展空间。

### 7.4 现场问题建议字段

| 字段 | 说明 |
|---|---|
| 所属检查任务 | 必填 |
| 所属日报 | 必填 |
| 问题来源 | 表内问题 / 表外问题 |
| 关联检查项 | 表内问题必填，表外问题为空 |
| 问题描述 | 检查员填写 |
| 责任单位 | 必填 |
| 问题分类 | 可选或必填，按设计决定 |
| 严重等级 | 一般 / 较大 / 重大 |
| 判定依据 | 标准条款或人工说明 |
| 整改建议 | V1 可填写，后续整改闭环使用 |
| 照片 | 一条问题可多张 |
| 创建人 | 检查员 |
| 创建时间 | 系统记录 |

### 7.5 照片规则

1. 一个问题可以有多张照片。
2. 照片属于问题。
3. 照片可以用于日报、周报、月报。
4. 报告中使用哪些照片，应在报告问题快照中保存引用。
5. V1 至少应区分现场拍照与补充照片，便于后续取证和报告展示。

---

## 8. 日报 Daily Report

### 8.1 日报的业务含义

日报是检查员当天现场检查成果的载体。

现场检查发现的问题先进入日报。

日报是问题台账的唯一来源。

### 8.2 日报包含内容

日报至少包含：

| 内容 | 说明 |
|---|---|
| 所属项目 | 必填 |
| 检查任务 | 可关联一个或多个，按设计决定 |
| 检查员 | 必填 |
| 检查日期 | 必填 |
| 检查地点 | 实际地点 |
| 实际受检单位 | 现场填写 |
| 当天检查情况 | 检查员填写 |
| 当天发现问题 | 日报问题 |
| 问题照片 | 来源于问题 |
| 明日计划 | 检查员填写 |
| 状态 | 草稿 / 已提交 / 已退回 / 已确认 / 已锁定 / 已导出 |

### 8.3 日报与问题台账

固定规则：

```text
只有日报中的有效问题，才能进入问题台账。
```

### 8.4 日报状态建议

| 状态 | 含义 |
|---|---|
| 草稿 | 检查员编辑中，不进入台账 |
| 已提交 | 检查员提交，日报问题进入台账，台账状态为待确认 |
| 已退回 | 被退回修改，相关台账问题暂停使用或标记待修改 |
| 已确认 | 日报通过确认，台账问题成为有效问题 |
| 已锁定 | 日报不可再修改 |
| 已导出 | 已生成文件 |

### 8.5 日报审核配置

日报是否需要组长确认、是否需要报告审核人审核，不写死，由项目配置决定。

V1 提供功能，生产环境由用户根据项目需要配置。

## 9. 问题台账 Issue Ledger

### 9.1 业务含义

问题台账是日报问题的汇总池和主数据源。

问题台账不是人工随意录入问题的入口。

问题台账的唯一来源是日报。

### 9.2 追溯要求

台账问题必须能追溯到：

```text
台账问题
  → 来源日报
  → 来源检查任务
  → 来源检查员
  → 来源项目检查表
  → 来源检查项或表外问题
  → 来源照片
```

### 9.3 问题台账建议字段

| 字段 | 说明 |
|---|---|
| 问题编号 | 系统生成，固定不变 |
| 所属项目 | 来源日报所属项目 |
| 来源日报 | 必填 |
| 来源日报问题 | 必填 |
| 来源检查任务 | 必填 |
| 检查员 | 必填 |
| 责任单位 | 快照 |
| 问题描述 | 来源日报问题 |
| 判定依据 | 来源日报问题 |
| 整改建议 | 来源日报问题 |
| 严重等级 | 来源日报问题 |
| 台账状态 | 待确认 / 有效 / 作废 |
| 是否纳入正式报告 | 系统计算或标记 |
| 创建时间 | 系统记录 |

### 9.4 台账状态建议

| 状态 | 含义 |
|---|---|
| 待确认 | 日报提交后进入台账，但尚未确认 |
| 有效 | 日报确认后成为有效台账问题 |
| 作废 | 经审核认为不作为有效问题 |
| 暂停使用 | 日报退回或问题需修改时临时状态，可选 |

### 9.5 台账业务规则

1. 问题台账只从日报生成。
2. 周报/月报只能从问题台账选择问题。
3. 台账问题保存原始问题事实。
4. 报告中的问题表述可以不同，但不得覆盖台账原始问题。
5. 台账问题需要保留后续整改接口字段。

## 10. 周报/月报 Report

### 10.1 业务含义

周报、月报是对甲方交付的正式产品，不是临时查询结果。

周报、月报从问题台账选择问题生成。

周报、月报经过审核并发布后，作为 V1 的正式交付成果。

### 10.2 周报/月报来源规则

周报/月报不能：

1. 直接新增问题；
2. 直接引用现场检查记录；
3. 直接引用日报草稿问题；
4. 重复选择同一个台账问题到同一份报告。

周报/月报可以：

1. 从问题台账选择问题；
2. 调整报告内展示顺序；
3. 修改报告内问题表述；
4. 修改报告内依据、整改建议、责任单位表述；
5. 选择报告内使用的照片；
6. 补充报告分析和建议；
7. 保存报告问题快照。

### 10.3 周报/月报问题描述

周报/月报中的问题描述可以和问题台账不一致。

原因：

1. 台账保存现场原始事实记录。
2. 周报/月报面对甲方，需要正式、规范、可交付的表达。
3. 领导或组长审核时可能调整措辞。
4. 后期整改如果依据正式交付文件，应以发布报告中的问题快照为准。

固定规则：

```text
台账问题 = 原始事实记录
报告问题快照 = 对外正式表述
```

## 11. 报告问题快照 Report Issue Snapshot

### 11.1 业务含义

报告问题快照保存报告中使用的问题内容。

它引用问题台账，但不覆盖问题台账。

### 11.2 建议字段

| 字段 | 说明 |
|---|---|
| 报告ID | 所属日报/周报/月报 |
| 台账问题ID | 周报/月报必填 |
| 日报问题ID | 日报可直接引用 |
| 问题描述快照 | 报告内正式表述 |
| 责任单位快照 | 报告内使用的责任单位 |
| 判定依据快照 | 报告内使用的依据 |
| 整改建议快照 | 报告内使用的建议 |
| 照片引用快照 | 报告内使用的照片 |
| 展示顺序 | 报告内排序 |

### 11.3 唯一约束

周报/月报必须设置唯一约束：

```text
report_id + ledger_issue_id 唯一
```

业务含义：

1. 同一个台账问题不能在同一份周报/月报中出现两次。
2. 同一个台账问题可以进入周报，也可以进入月报。
3. 报告内修改的是快照，不修改台账原文。

## 12. 报告审核与发布

### 12.1 报告类型

系统支持：

```text
日报
周报
月报
```

### 12.2 审核流程可配置

审核流程不写死，由项目配置决定。

默认建议：

| 报告类型 | 默认流程 |
|---|---|
| 日报 | 检查员创建 → 组长确认 → 锁定 |
| 周报 | 检查员创建 → 组长复核 → 报告审核人审核 → 发布 |
| 月报 | 检查员创建 → 组长复核 → 报告审核人审核 → 发布 |

项目可以配置：

| 配置项 | 说明 |
|---|---|
| 是否需要组长确认 | 按报告类型配置 |
| 是否需要报告审核人审核 | 按报告类型配置 |
| 审核通过后是否允许发布 | 按报告类型配置 |
| 审核人角色 | 默认报告审核人 |

### 12.3 报告审核人

“领导”在系统中抽象为一个角色：

```text
报告审核人
```

生产环境中由管理员给具体用户分配该角色。

### 12.4 报告状态建议

V1 不做独立归档模块，报告状态建议为：

| 状态 | 含义 |
|---|---|
| 草稿 | 检查员编辑中 |
| 待组长确认 | 提交组长复核 |
| 待报告审核人审核 | 组长提交审核 |
| 已退回 | 被退回修改 |
| 审核通过 | 内部确认完成，等待发布 |
| 已发布 | 已作为正式产品交付甲方，锁定不可改 |
| 已作废 | 发布前或异常情况下作废 |

### 12.5 发布规则

V1 做到发布，不做归档模块。

但发布必须具备固化效果。

发布时必须固化：

| 内容 | 说明 |
|---|---|
| 报告基本信息 | 项目、报告类型、周期、创建人等 |
| 报告正文 | 发布时的正文内容 |

### 12.6 发布后修改规则

## 17. 业主补充需求影响结论

业主补充的拍照、问题描述、标准对标、问题分级、位置关联、判定依据、整改建议、专家交流、远程控制、报告样式定制等需求，不推翻已经确定的主业务链。


核心数据来源规则仍为：


### 17.1 不改变的规则

1. 项目仍然是业务源头。
2. 项目检查表仍然属于项目。
3. 组长派发检查任务。
4. 检查员现场检查后形成日报。

4. 语音备注可选，但不能替代文字问题描述。
5. 标准问题库是核心基础数据，管理员可动态维护。

8. 判定依据允许人工补充。
9. 严重等级为一般、较大、重大。

11. 重大问题可预留电话通知记录。
12. 问题必须关联责任单位和具体位置。

15. PC 端支持日报、周报、月报、统计表的模板化导出。

## 18. 统一组织机构管理

### 18.1 业务结论

系统采用统一组织机构管理。

组织机构用于维护：

1. 甲方单位；
2. 甲方分公司；
3. 作业区；
4. 站场；
5. 阀室；
6. 施工单位；
7. 监理单位；
8. 检测单位；
9. 第三方检查机构；
10. 其他相关单位。

组织机构只录入一次，后续在项目、日报、问题、报告、后续整改中重复引用。

### 18.2 组织机构支持层级关系

组织机构支持上下级树形结构。

示例：

```text
甘肃公司
  ├── 兰州输油气分公司
  │     ├── 白银天然气分输站
  │     └── 景泰输气站
  └── 酒泉输油气分公司
        ├── 玉门作业区
        └── 某阀室
```

每一级组织节点必须设置机构类别。

### 18.3 机构类别与项目角色必须分开

固定规则：

```text
机构类别 = 这个节点本身是什么
项目角色 = 这个节点在某个项目中承担什么业务身份
```

示例：

| 组织机构 | 机构类别 | 项目角色 |
|---|---|---|
| 甘肃公司 | 甲方公司 | 甲方单位 |
| 兰州输油气分公司 | 甲方分公司 | 受检分公司 |
| 白银天然气分输站 | 站场 | 检查地点 |
| 石兰线 6# 阀室 | 阀室 | 检查地点 |
| 安徽省防腐工程总公司 | 施工单位 | 被检查单位 / 责任单位 |
| 大庆市励丰工程监理有限公司 | 监理单位 | 被检查单位 / 责任单位 |
| 中国船级社质量认证有限公司 | 第三方检查机构 | 检查执行单位 |

## 19. 日报与检查任务的关系

### 19.1 定版结论

固定规则：

```text
一份日报只能属于一个项目。
一份日报只能属于一个检查员。
一份日报可以关联同一项目下该检查员当天的多个检查任务。
```

### 19.2 限制条件

1. 多个检查任务必须属于同一个项目。
2. 多个检查任务必须分配给同一个检查员。
3. 多个检查任务原则上属于同一天。
4. 一份日报不能跨项目。
5. 一份日报不能跨检查员。
6. 一个检查任务同一时间只能关联一份有效日报。

### 19.3 关系模型

```text
检查任务 A
检查任务 B
检查任务 C
   ↓
同一份日报
```

日报的本质是“检查员当天现场检查成果”，不是单个检查任务的结果。

### 19.4 DailyReportTask 日报任务关联表

字段建议：

| 字段 | 说明 |
|---|---|
| daily_report_id | 日报 ID |
| inspection_task_id | 检查任务 ID |
| project_id | 冗余保存，便于校验 |
| inspector_id | 冗余保存，便于校验 |
| task_name_snapshot | 任务名称快照 |
| inspection_form_id | 检查表 ID |
| inspection_form_version | 检查表版本 |

约束：

```text
inspection_task_id + daily_report_id 唯一
```

业务上应保证：

```text
一个检查任务同一时间只能关联一份有效日报。
```

### 19.5 日报与任务状态联动

| 日报动作 | 日报状态 | 检查任务状态 | 台账处理 |
|---|---|---|---|
| 创建日报草稿 | 草稿 | 执行中 | 不生成台账 |
| 提交日报 | 已提交 | 已提交日报 | 生成台账问题，状态=待确认 |
| 退回日报 | 已退回 | 日报退回待修改 | 台账问题暂停使用 |
| 确认日报 | 已确认 / 已锁定 | 已完成 | 台账问题变为有效 |
| 作废日报 | 已作废 | 视情况恢复或取消 | 台账问题作废 |

### 19.6 检查任务状态修正

检查任务状态建议为：

```text
待执行
执行中
已提交日报
日报退回待修改
已完成
已取消
```

说明：

| 状态 | 含义 |
|---|---|
| 待执行 | 组长已派发，检查员未开始 |
| 执行中 | 检查员已开始检查或正在编辑日报 |
| 已提交日报 | 检查员已提交日报，等待确认 |
| 日报退回待修改 | 日报被退回，需要检查员修改 |
| 已完成 | 日报确认后，任务完成 |
| 已取消 | 组长取消任务 |

## 21. 日报提交后问题台账生成、退回、修改、作废规则

### 21.1 核心原则

固定规则：

```text
日报问题是来源记录。
问题台账是从日报问题生成的管理记录。
周报/月报只能选择“有效”的台账问题。
```

状态链固定为：

```text
日报草稿
  ↓
日报提交
  ↓
生成台账问题：待确认
  ↓
日报确认
  ↓
台账问题：有效
  ↓
周报/月报可选择
```

数据链固定为：

```text
日报问题 → 台账问题 → 报告问题快照
```

### 21.2 日报草稿阶段

日报草稿阶段不生成台账问题。

规则：

1. 日报草稿中的问题只存在于日报问题表。
2. 日报草稿问题不能进入问题台账。
3. 日报草稿问题不能被周报/月报选择。
4. 日报草稿问题不作为正式整改依据。
5. 日报草稿问题不参与正式统计。

原因：

1. 检查员仍在编辑。
2. 问题可能被删除、修改、拆分、合并。
3. 照片可能未上传完整。
4. 责任单位、依据、整改建议可能未填写完整。
5. 草稿数据进入台账会产生脏数据。

### 21.3 日报提交校验

日报提交时必须先进行完整性校验。

| 校验项 | 规则 |
|---|---|
| 项目 | 必填 |
| 检查员 | 必填 |
| 检查日期 | 必填 |
| 检查任务 | 至少关联一个 |
| 实际受检单位 | 至少一个 |
| 问题描述 | 每条问题不少于 100 字 |
| 责任单位 | 每条问题必填 |
| 严重等级 | 每条问题必填 |
| 位置 | 站场/阀室或具体区域按项目配置必填 |
| 判定依据 | 有标准依据或填写无依据说明 |
| 照片 | 是否必填按项目配置，默认建议必填 |
| 表内问题 | 必须关联检查项 |
| 不适用检查项 | 必须填写原因 |
| 未检查检查项 | 必须填写原因 |

校验不通过，不允许提交日报。

### 21.4 日报提交时生成台账问题

日报提交成功后，系统执行：

```text
日报状态 = 已提交
检查任务状态 = 已提交日报
日报中的有效问题生成台账问题
台账问题状态 = 待确认
```

台账问题必须记录来源：

| 字段 | 说明 |
|---|---|
| 来源日报 ID | 必填 |
| 来源日报问题 ID | 必填 |
| 来源检查任务 ID | 必填 |
| 来源检查员 ID | 必填 |
| 来源项目检查表 ID | 必填 |
| 来源检查项 ID | 表内问题必填 |
| 问题来源 | 表内 / 表外 |

固定规则：

```text
没有来源日报问题的记录，不能进入问题台账。
```

### 21.5 日报确认前的台账问题

日报提交后、确认前，台账问题状态为：

```text
待确认
```

待确认台账问题的规则：

1. 可以在问题台账中查看。
2. 不能进入周报/月报。
3. 不能作为正式整改依据。
4. 不能进入已发布报告。
5. 不参与正式统计。
6. 仅用于待确认问题查看和追溯。

固定规则：

```text
只有“有效”的台账问题，才能被周报/月报选择。
```

### 21.6 日报确认时

日报确认后：

```text
日报状态 = 已确认 / 已锁定
关联检查任务状态 = 已完成
台账问题状态 = 有效
```

有效台账问题可以：

1. 被周报选择；
2. 被月报选择；
3. 参与正式统计；
4. 作为后续整改依据；
5. 在问题台账中长期保留。

### 21.7 日报退回时

日报退回时，不直接删除已生成的台账问题。

固定规则：

```text
日报退回后，已生成的台账问题状态改为“暂停使用”。
```

状态变化：

```text
日报状态 = 已退回
检查任务状态 = 日报退回待修改
台账问题状态 = 暂停使用
```

暂停使用的台账问题：

1. 不可进入周报/月报；
2. 不参与正式统计；
3. 不作为整改依据；
4. 只用于追溯；
5. 保留原问题编号和来源关系。

### 21.8 日报退回后重新提交

日报退回后重新提交，采用：

```text
优先更新原台账问题。
```

不默认作废旧台账、重新生成新台账。

| 修改场景 | 台账处理 |
|---|---|
| 修改问题描述 | 更新原台账问题 |
| 修改责任单位 | 更新原台账问题，并保留新责任单位快照 |
| 修改判定依据 | 更新原台账问题 |
| 修改整改建议 | 更新原台账问题 |
| 修改照片 | 更新原台账问题的照片引用 |
| 删除日报问题 | 对应台账问题标记为作废 |
| 新增日报问题 | 生成新的台账问题 |
| 一个问题拆分为多个问题 | 原台账问题作废，拆分后的问题生成新台账问题 |
| 多个问题合并为一个问题 | 被合并问题作废，保留主问题或生成合并后问题 |

该规则的目的：

1. 尽量保持问题编号稳定。
2. 避免产生大量无意义作废记录。
3. 保留必要的历史追溯。
4. 支撑后续报告和整改引用。

### 21.9 日报确认后修改规则

固定原则：

```text
日报确认后，不能直接修改。
```

V1 简化规则：

```text
已确认日报原则上不允许修改。
如确需修改，由组长或管理员作废日报后重新创建或重新提交。
```

后续版本可扩展“日报更正流程”。

### 21.10 台账问题作废规则

台账问题可以作废，但必须区分是否已经进入已发布报告。

#### 21.10.1 未进入已发布报告

如果台账问题还没有进入已发布周报/月报，可以作废。

作废后：

1. 不可再进入周报/月报。
2. 不参与正式统计。
3. 不作为整改依据。
4. 保留作废原因、作废人、作废时间。
5. 保留来源日报、来源日报问题、来源检查任务等追溯关系。

#### 21.10.2 已进入已发布报告

如果台账问题已经进入已发布报告，不能直接作废。

固定规则：

```text
已进入已发布报告的台账问题，只能标记为“后续更正”，不能直接删除或普通作废。
```

建议字段：

| 字段 | 说明 |
|---|---|
| 更正状态 | 未更正 / 已更正 |
| 更正说明 | 为什么更正 |
| 更正人 | 谁更正 |
| 更正时间 | 什么时候更正 |
| 关联更正报告 | 如果重新发布报告，记录新报告 |

### 21.11 台账问题状态

台账状态固定为：

```text
待确认
有效
暂停使用
作废
后续更正
```

| 状态 | 含义 | 能否进周报/月报 |
|---|---|---|
| 待确认 | 日报已提交，尚未确认 | 否 |
| 有效 | 日报已确认，可正式使用 | 是 |
| 暂停使用 | 日报退回或问题待修改 | 否 |
| 作废 | 未进入正式报告前被作废 | 否 |
| 后续更正 | 已进入发布报告后发现需纠正 | 否，仅用于追溯和纠错说明 |

### 21.12 最终定版规则

1. 日报草稿不生成问题台账。
2. 日报提交时，系统对日报完整性进行校验。
3. 校验通过后，日报中的有效问题生成问题台账记录。
4. 日报提交后，台账状态为“待确认”。
5. 日报确认前，台账问题不能被周报/月报选择，也不能作为正式整改依据。
6. 日报确认后，台账问题状态变为“有效”。
7. 只有有效台账问题，才能进入周报/月报。
8. 日报退回后，已生成的台账问题状态变为“暂停使用”。
9. 日报重新提交后，系统优先更新原台账问题。
10. 删除的问题对应台账问题作废。
11. 新增的问题生成新台账问题。
12. 拆分或合并的问题按作废旧问题、生成或保留主问题处理。
13. 已确认日报原则上不允许直接修改。
14. V1 如需修改已确认日报，由组长或管理员作废后重新创建或重新提交。
15. 未进入已发布报告的台账问题可以作废。
16. 已进入已发布报告的台账问题不能直接作废，只能标记为“后续更正”。
17. 台账问题必须保留来源日报、来源日报问题、来源检查任务、来源检查员、来源检查表、来源检查项或表外问题等追溯关系。

## 23. 已发布报告变更、作废、重发规则

### 23.1 核心原则

固定规则：

```text
已发布报告不可直接编辑。
```

原因：

1. 已发布报告已经作为正式交付物交付甲方。
2. 报告正文、报告问题快照、照片引用、审核记录、导出文件已经固化。
3. 后续整改可能引用已发布报告的问题快照。
4. 如果允许直接修改，会导致系统数据、报告文件、审核责任不一致。
5. 发布即固化，必须可追溯。

因此，已发布报告不能直接修改，只能通过“变更报告”入口处理。

---

### 23.2 用户操作入口

在已发布报告详情页提供按钮：

```text
变更报告
```

用户点击后，系统提示：

```text
已发布报告不可直接修改。如需调整，请选择变更方式。系统将基于当前报告生成新的变更草稿，原报告和历史版本将保留。
```

用户不需要理解内部的“已被替代、报告问题快照、root_report_id、previous_report_id”等技术概念，只需要选择变更方式。

---

### 23.3 报告变更方式

报告变更方式固定为五类：

```text
1. 文字/格式更正
2. 问题内容更正
3. 补充问题
4. 移除问题
5. 整体作废重发
```

---

### 23.4 文字/格式更正

适用场景：

1. 错别字；
2. 语句不通顺；
3. 格式问题；
4. 标题错误；
5. 页眉页脚问题；
6. 页码、排版问题；
7. 不影响问题事实的文字优化。

系统处理：

```text
复制原报告
  ↓
生成变更草稿
  ↓
修改文字/格式
  ↓
重新审核
  ↓
重新发布新版本
```

规则：

1. 原报告不删除。
2. 原报告发布快照不修改。
3. 新报告发布后成为当前有效版本。
4. 原报告标记为“已被替代”。
5. 主报告编号不变，版本号递增。

---

### 23.5 问题内容更正

适用场景：

1. 问题描述需要调整；
2. 判定依据需要调整；
3. 整改建议需要调整；
4. 责任单位表述需要调整；
5. 严重等级表述需要调整；
6. 报告中问题表达不够正式或不够准确。

系统处理：

```text
复制原报告正文和问题快照
  ↓
生成变更草稿
  ↓
允许修改报告问题快照
  ↓
重新审核
  ↓
重新发布新版本
```

规则：

1. 修改的是新版本报告的问题快照。
2. 不覆盖问题台账原文。
3. 不修改旧版本报告快照。
4. 如果更正涉及台账事实、责任单位、依据、等级等，应在台账中记录“后续更正”或建立更正关联记录。
5. 新报告发布后成为当前有效版本。
6. 原报告标记为“已被替代”。

---

### 23.6 补充问题

适用场景：

```text
已发布报告漏选了应纳入的问题。
```

系统处理：

```text
复制原报告
  ↓
生成变更草稿
  ↓
允许从有效台账中补选问题
  ↓
生成新增报告问题快照
  ↓
重新审核
  ↓
重新发布新版本
```

规则：

1. 只能从有效台账问题中选择。
2. 不能在报告变更中直接新建问题。
3. 新增问题形成新版本报告的问题快照。
4. 原报告问题快照不修改。
5. 新报告发布后成为当前有效版本。
6. 原报告标记为“已被替代”。

---

### 23.7 移除问题

适用场景：

```text
已发布报告误选了不应纳入的问题。
```

系统处理：

```text
复制原报告
  ↓
生成变更草稿
  ↓
移除误选问题快照
  ↓
填写移除原因
  ↓
重新审核
  ↓
重新发布新版本
```

规则：

1. 移除的是新版本报告中的问题快照。
2. 旧版本报告快照仍然保留。
3. 如果误选问题涉及台账纠错，台账记录“后续更正”。
4. 新报告发布后成为当前有效版本。
5. 原报告标记为“已被替代”。

---

### 23.8 整体作废重发

适用场景：

1. 报告周期错误；
2. 报告项目错误；
3. 报告类型错误；
4. 报告数据范围错误；
5. 导出文件错误；
6. 整体内容不应作为正式交付物；
7. 原报告整体不再成立。

系统处理：

```text
原报告标记为已作废
  ↓
填写作废原因
  ↓
复制生成新草稿或重新创建报告
  ↓
重新审核
  ↓
重新发布
```

规则：

1. 原报告状态变为“已作废”。
2. 必须填写作废原因。
3. 作废报告、作废前的报告问题快照、导出文件、审核记录必须保留。
4. 系统可复制原报告生成新草稿，也可重新创建报告。
5. 整体作废重发是否沿用原编号，由项目配置决定。
6. 默认建议：普通更正沿用主编号并递增版本；整体作废重发生成新编号。如甲方要求同编号，可通过版本号区分。

---

### 23.9 用户界面展示建议

用户点击“变更报告”后，界面显示：

```text
请选择变更方式：

1. 文字/格式更正
   修改错别字、格式、标题、页眉页脚等，不影响问题事实。

2. 问题内容更正
   修改问题描述、依据、整改建议、责任单位表述、严重等级等。

3. 补充问题
   将漏选的有效台账问题补充到报告中。

4. 移除问题
   从新版本报告中移除误选问题。

5. 整体作废重发
   当前报告整体不再作为有效交付物，重新生成报告。
```

### 23.10 内部状态处理规则

| 用户选择 | 原报告状态 | 新报告状态 | 编号规则 |
|---|---|---|---|
| 文字/格式更正 | 已被替代 | 草稿 → 审核 → 已发布 | 主编号不变，版本 +1 |
| 问题内容更正 | 已被替代 | 草稿 → 审核 → 已发布 | 主编号不变，版本 +1 |
| 补充问题 | 已被替代 | 草稿 → 审核 → 已发布 | 主编号不变，版本 +1 |
| 移除问题 | 已被替代 | 草稿 → 审核 → 已发布 | 主编号不变，版本 +1 |
| 整体作废重发 | 已作废 | 新草稿 → 审核 → 已发布 | 默认新编号，可按项目配置沿用编号并版本 +1 |

---

### 23.11 报告版本关系

报告必须保存版本关系。

建议报告字段增加：

| 字段 | 说明 |
|---|---|
| report_version | 报告版本号 |
| previous_report_id | 上一版报告 ID |
| root_report_id | 最初报告 ID |
| replace_reason | 替代原因 |
| void_reason | 作废原因 |
| correction_type | 文字/格式更正、问题内容更正、补充问题、移除问题、整体作废重发 |
| is_current_effective | 是否当前有效版本 |

系统必须能查询：

1. 当前有效版本是哪一份；
2. 当前报告替代了哪一版；
3. 当前报告的第一版是哪一份；
4. 当前报告为什么变更；
5. 历史版本有哪些；
6. 每个版本对应哪些问题快照和导出文件。

---

### 23.12 报告编号与版本号

报告编号规则固定为：

```text
同一份报告的更正：主编号不变，版本号递增。
整体作废重发：默认生成新编号；如项目配置要求同编号，则原编号版本号递增。
```

示例：

```text
WR-20250707-001 v1
WR-20250707-001 v2
WR-20250707-001 v3
```

说明：

1. 第一次发布为 v1。
2. 更正重发为 v2。
3. 再次更正为 v3。
4. 完全新报告生成新主编号。

---

### 23.13 报告问题快照规则

固定规则：

```text
每次发布都生成独立的报告正文快照、报告问题快照和导出文件。
```

不能让新版本覆盖旧版本快照。

正确结构：

```text
报告 v1
  ├── v1 报告正文快照
  ├── v1 问题快照
  └── v1 导出文件

报告 v2
  ├── v2 报告正文快照
  ├── v2 问题快照
  └── v2 导出文件
```

规则：

1. v1 快照永久保留。
2. v2 重新生成自己的快照。
3. v2 可以复制 v1 快照作为初始内容。
4. 修改 v2 不影响 v1。
5. 后续整改默认引用当前有效版本。

---

### 23.14 导出文件固化规则

每次发布都必须保存：

| 字段 | 说明 |
|---|---|
| 导出文件路径 | Word 文件路径 |
| 导出时间 | 系统记录 |
| 导出人 | 系统记录 |
| 报告版本 | 当前版本 |
| 文件哈希值 | 可选，用于防篡改或一致性校验 |

固定规则：

```text
发布一次，固化一次导出文件。
```

旧版本文件不得被覆盖。

---

### 23.15 台账“后续更正”与报告变更关系

报告变更不一定影响台账。

如果只是文字、格式问题，不需要更新台账。

如果报告变更涉及以下内容，应在台账中记录“后续更正”或更正关联记录：

1. 问题误选；
2. 问题事实错误；
3. 责任单位错误；
4. 严重等级错误；
5. 判定依据错误；
6. 整改建议错误。

注意：

```text
报告更正不覆盖台账原文。
```

报告更正修改的是：

```text
报告问题快照
```

台账上只记录：

```text
该台账问题在某份已发布报告中发生过更正。
```

可选扩展对象：

```text
LedgerCorrectionRecord 台账更正记录
```

建议字段：

| 字段 | 说明 |
|---|---|
| ledger_issue_id | 台账问题 |
| original_report_id | 原报告 |
| corrected_report_id | 更正后报告 |
| correction_reason | 更正原因 |
| correction_type | 责任单位更正 / 描述更正 / 依据更正 / 等级更正 / 误选剔除 / 其他 |
| created_by | 操作人 |
| created_at | 操作时间 |

V1 如果不单独建表，也至少要在台账中保留：

1. 更正状态；
2. 更正说明；
3. 关联更正报告。

---

### 23.16 后续整改引用规则

虽然 V1 不做整改闭环，但必须预留原则。

固定规则：

```text
后续整改默认引用当前有效发布版本的报告问题快照。
```

后续整改需预留字段：

| 字段 | 说明 |
|---|---|
| source_report_id | 整改来源报告 |
| source_report_version | 整改来源报告版本 |
| source_report_issue_snapshot_id | 整改来源问题快照 |

如果某个问题已经在 v1 形成整改，后来报告 v2 更正，不能自动改掉历史整改依据。

历史整改依据应记录其当时引用的报告版本和问题快照。

---

### 23.17 最终定版规则

1. 已发布报告不可直接编辑。
2. 用户需要调整已发布报告时，在报告详情页点击“变更报告”。
3. 报告变更方式包括：文字/格式更正、问题内容更正、补充问题、移除问题、整体作废重发。
4. 除“整体作废重发”外，其余变更均采用“复制原报告生成变更草稿 → 修改 → 重新审核 → 重新发布”的方式处理。
5. 重新发布后，新报告成为当前有效版本。
6. 原报告标记为“已被替代”。
7. 原报告、原报告问题快照、原导出文件、原审核记录必须保留。
8. 整体作废重发时，原报告标记为“已作废”，必须填写作废原因。
9. 系统可复制原报告生成新草稿，也可重新创建报告。
10. 所有变更必须填写变更原因。
11. 系统必须保存变更方式、发起人、发起时间、原报告、新报告、审核记录。
12. 报告主编号原则上保持不变，通过版本号区分 v1、v2、v3。
13. 整体作废重发是否生成新编号，可按项目配置。
14. 每次发布都生成独立报告正文快照、报告问题快照和导出文件。
15. 旧版本快照和旧版本导出文件不得被覆盖。
16. 后续整改默认引用当前有效发布版本的报告问题快照。
17. 如果报告变更涉及台账事实、责任单位、依据、等级、误选等，应在台账中记录“后续更正”或建立更正关联记录。

## 24. 通用简单审批流程配置

### 24.1 核心结论

业主公司规模约 20 多人，系统不应设计复杂审批流。

固定规则：

```text
流程问题交由用户按项目配置。

系统不内置复杂审批流，不写死日报、周报、月报的具体审核路径。

V1 只提供通用、简单、可自定义配置的审批能力。
```

系统目标不是做复杂工作流引擎，而是满足小团队项目管理中常见的提交、审批、退回、发布、作废、变更留痕需求。

---

### 24.2 不做复杂工作流

V1 不做以下复杂能力：

1. 条件分支；
2. 会签；
3. 或签；
4. 加签；
5. 转审；
6. 抄送；
7. 超时自动处理；
8. 动态表达式；
9. 多级复杂审批链；
10. 流程设计器；
11. BPMN 工作流引擎。

这些能力对当前项目过重，会增加使用成本和开发复杂度。

---

### 24.3 V1 支持的审批模式

V1 只支持三种简单模式：

```text
无审批
一级审批
两级审批
```

#### 24.3.1 无审批

```text
创建草稿 → 发布
```

适用于：

1. 内部临时日报；
2. 简单统计表；
3. 不需要正式审核的内部材料。

#### 24.3.2 一级审批

```text
创建草稿 → 提交 → 审批通过 → 发布
```

适用于：

1. 普通日报；
2. 简单周报；
3. 项目内部确认材料。

#### 24.3.3 两级审批

```text
创建草稿 → 提交 → 一级审批通过 → 二级审批通过 → 发布
```

适用于：

1. 正式周报；
2. 正式月报；
3. 对甲方交付的正式报告；
4. 已发布报告变更。

---

### 24.4 审批对象

通用审批能力适用于：

1. 日报；
2. 周报；
3. 月报；
4. 报告变更。

后续如增加总结报告、整改报告，也复用同一套通用审批能力。

---

### 24.5 项目级流程配置

项目中增加配置入口：

```text
项目设置 → 流程配置
```

按对象类型分别配置：

```text
日报流程
周报流程
月报流程
报告变更流程
```

每类流程配置项：

| 配置项 | 说明 |
|---|---|
| 是否启用审批 | 是 / 否 |
| 审批模式 | 无审批 / 一级审批 / 两级审批 |
| 一级审批人 | 角色或指定用户 |
| 二级审批人 | 角色或指定用户 |
| 是否需要单独发布 | 是 / 否 |
| 发布人 | 角色或指定用户 |
| 退回后去向 | 固定回到创建人草稿 |
| 是否允许变更已发布报告 | 是 / 否 |
| 变更后是否重新审批 | 是，固定要求 |

---

### 24.6 审批节点配置方式

审批节点可以配置为：

1. 角色；
2. 指定用户。

角色示例：

1. 组长；
2. 报告审核人；
3. 管理员。

指定用户示例：

1. 张三；
2. 李四；
3. 项目负责人。

固定规则：

```text
审批节点配置为角色时，拥有该角色且在项目范围内的用户可以处理审批。

审批节点配置为指定用户时，只有该用户可以处理审批。
```

---

### 24.7 默认流程模板

系统可以提供默认模板，但模板只是初始配置，不是强制业务规则。

建议默认模板：

| 模板 | 流程 |
|---|---|
| 无审批模板 | 草稿 → 发布 |
| 一级审批模板 | 草稿 → 提交 → 审批通过 → 发布 |
| 两级审批模板 | 草稿 → 提交 → 一级审批通过 → 二级审批通过 → 发布 |

用户创建项目时，可以选择模板，也可以后续调整。

---

### 24.8 统一状态

不要把状态写死为“待组长确认”“待报告审核人审核”。

统一使用通用状态：

```text
草稿
待审批
审批中
已退回
审批通过
已发布
已作废
已被替代
```

说明：

| 状态 | 含义 |
|---|---|
| 草稿 | 创建人编辑 |
| 待审批 | 已提交，等待第一个审批节点处理 |
| 审批中 | 已通过部分节点，还有后续审批节点 |
| 已退回 | 被审批人退回 |
| 审批通过 | 所有配置审批节点已通过，等待发布 |
| 已发布 | 正式发布，锁定 |
| 已作废 | 作废，不再作为有效文件 |
| 已被替代 | 已发布后被新版本替代 |

---

### 24.9 审批通过与发布的关系

固定规则：

```text
审批通过不等于发布。
```

系统支持配置：

1. 审批通过后需要单独发布；
2. 审批通过后自动发布。

V1 默认建议：

```text
审批通过后需要单独发布。
```

原因：

1. 发布是正式交付动作；
2. 发布时需要固化报告快照和导出文件；
3. 发布动作需要单独留痕；
4. 小团队中通常由项目负责人最终点击发布更清晰。

---

### 24.10 退回规则

固定规则：

```text
退回后统一回到创建人草稿。
```

不做复杂退回路径。

原因：

1. 用户容易理解；
2. 实现简单；
3. 避免流程卡住；
4. 创建人修改后重新提交完整流程。

日报退回后：

```text
日报状态 = 已退回
检查任务状态 = 日报退回待修改
台账问题状态 = 暂停使用
```

周报、月报、报告变更退回后：

```text
报告状态 = 已退回
退回到创建人草稿
重新提交后按配置流程重新审批
```

已发布报告变更草稿退回后：

```text
变更草稿状态 = 已退回
原已发布报告仍保持当前有效
```

固定规则：

```text
变更草稿未发布前，不影响原已发布报告。
```

---

### 24.11 通用权限

V1 不做过细的业务权限矩阵，先做通用权限。

| 权限 | 说明 |
|---|---|
| 创建 | 能创建日报、报告、变更草稿 |
| 编辑草稿 | 能编辑未提交对象 |
| 提交审批 | 能提交 |
| 审批 | 能处理分配给自己的审批节点 |
| 发布 | 能发布审批通过的报告 |
| 作废 | 能作废草稿、未发布报告或按规则作废已发布报告 |
| 变更报告 | 能对已发布报告发起变更 |
| 查看 | 能查看项目内数据 |

审批节点由项目流程配置决定谁能审批。

---

### 24.12 审批记录

虽然流程简化，但留痕不能省。

所有提交、审批、退回、发布、作废、变更动作都必须生成审批记录。

对象：

```text
ApprovalRecord 审批记录
```

字段建议：

| 字段 | 说明 |
|---|---|
| 业务对象类型 | 日报 / 周报 / 月报 / 报告变更 |
| 业务对象 ID | 对应对象 |
| 流程配置 ID | 当时采用的流程配置 |
| 流程节点序号 | 第几级审批 |
| 操作类型 | 提交 / 通过 / 退回 / 发布 / 作废 / 变更 |
| 操作人 | 系统记录 |
| 操作人角色快照 | 操作时角色 |
| 操作时间 | 系统记录 |
| 操作意见 | 可选 |
| 退回原因 | 退回必填 |
| 变更原因 | 报告变更必填 |
| 作废原因 | 作废必填 |
| 原状态 | 操作前状态 |
| 新状态 | 操作后状态 |

固定规则：

```text
审批记录不可修改、不可删除。
```

---

### 24.13 管理员越权处理

管理员可以越权处理异常流程，但必须留痕。

适用场景：

1. 流程卡住；
2. 人员离职；
3. 配置错误；
4. 误操作需要恢复；
5. 紧急交付。

管理员越权操作必须：

1. 填写越权原因；
2. 保存操作记录；
3. 标记为管理员操作；
4. 不覆盖原审批记录；
5. 不删除历史版本；
6. 不破坏已发布报告快照和导出文件。

---

### 24.14 最终定版规则

1. 业主公司规模约 20 多人，V1 不做复杂审批流。
2. 流程问题交由用户按项目配置。
3. 系统只提供通用、简单、可自定义配置的审批能力。
4. 系统不写死日报、周报、月报、报告变更的具体审核路径。
5. V1 支持无审批、一级审批、两级审批三种模式。
6. 审批对象包括日报、周报、月报、报告变更。
7. 审批节点可以配置为角色或指定用户。
8. 系统可以提供默认流程模板，但模板只是初始配置，不是强制业务规则。
9. 状态使用通用状态，不绑定具体角色名称。
10. 审批通过不等于发布，是否单独发布由项目配置决定；V1 默认建议单独发布。
11. 退回后统一回到创建人草稿。
12. 已发布报告变更草稿未发布前，不影响原已发布报告。
13. 所有提交、审批、退回、发布、作废、变更动作必须生成不可修改、不可删除的审批记录。
14. 管理员可以越权处理异常流程，但必须填写原因并留痕。
15. V1 不做条件分支、会签、或签、加签、转审、抄送、超时处理、流程设计器、BPMN 工作流引擎。

## 25. Web端、安卓端以用户目标为中心的设计原则

### 25.1 总体原则

系统不是单纯的数据录入系统，而是飞检业务效率工具。

固定规则：

```text
页面设计不能按数据库对象堆功能。
页面设计必须站在用户真实工作目标和当前操作步骤出发。
```

系统要做到：

1. 用户做到哪一步，系统就在那一步提供支持；
2. 用户没想到的问题，系统替用户提前考虑；
3. 用户不需要一次看到所有信息；
4. 系统不在入口处堆一堆无意义信息；
5. 页面越简洁，现场效率越高；
6. 简洁不是减少专业性，而是在正确时机给出正确提示。

---

### 25.2 Web端核心目标

Web端核心目标不是维护项目参与单位，也不是单纯管理基础数据。

Web端核心目标是：

```text
快速、准确、可控地生产高质量周报/月报，并支撑管理层判断项目进度、检查质量、交付风险和评审需求。
```

Web端应按不同用户提供不同工作视角。

#### 25.2.1 普通检查员视角

普通检查员在Web端的核心需求是：

```text
补充、整理、完善自己采集的问题素材。
```

重点能力：

1. 查看我的日报；
2. 查看我的问题素材；
3. 处理退回修改；
4. 补充问题描述；
5. 整理照片；
6. 补齐责任单位；
7. 补齐位置；
8. 补齐标准依据；
9. 采用或调整系统推荐标准；
10. 修改后重新提交。

普通检查员进入Web端后，系统应优先提示：

1. 哪些日报被退回；
2. 哪些问题描述不足；
3. 哪些问题缺少标准依据；
4. 哪些问题照片不完整；
5. 哪些问题责任单位或位置缺失；
6. 哪些问题会影响日报提交或报告生成。

#### 25.2.2 组长/项目负责人视角

组长、项目负责人的核心目标是：

```text
把检查员提交的现场素材加工成高质量周报/月报，并按时交付甲方。
```

重点能力：

1. 查看报告交付状态；
2. 查看待确认日报；
3. 查看待完善素材；
4. 查看有效问题台账；
5. 检查问题标准依据；
6. 检查照片证据质量；
7. 生成周报/月报草稿；
8. 编辑报告问题快照；
9. 提交审批；
10. 发布导出；
11. 发起已发布报告变更。

组长/项目负责人进入Web端后，系统应优先回答：

1. 本周/月报告能不能交；
2. 还缺哪些日报；
3. 哪些问题素材不完整；
4. 哪些问题没有标准依据；
5. 哪些照片不能支撑问题；
6. 哪些报告待审批或待发布；
7. 是否存在延期交付风险。

#### 25.2.3 管理层视角

管理层不关心每条数据怎么录入，而关心项目是否受控。

管理层核心问题包括：

1. 现在进度怎么样；
2. 检查员工作质量行不行；
3. 是否需要评审；
4. 是否能按时完成甲方任务；
5. 哪些项目或周期存在交付风险；
6. 哪些日报、问题、照片、依据还不完整；
7. 哪些检查员提交质量差、反复被退回；
8. 哪些问题严重等级较高，需要管理层关注；
9. 哪些责任单位问题集中，可能引发甲方关注；
10. 哪些标准依据缺失，报告可能站不住脚；
11. 哪些报告即将到期但还没生成或没发布；
12. 哪些问题已经进入报告但发生过后续更正；
13. 哪些项目检查覆盖不充分；
14. 哪些现场数据还没有同步；
15. 是否需要提前组织内部评审或专题会。

管理层页面不是普通统计图，而应是管理决策看板。

---

### 25.3 Web端管理决策看板

管理层看板应主动提示风险，而不是只展示数量。

建议分为以下区域：

#### 25.3.1 交付进度

回答：

```text
能不能按时完成甲方任务？
```

展示内容：

1. 本周报告状态；
2. 本月报告状态；
3. 报告计划交付时间；
4. 当前进度；
5. 剩余待处理事项；
6. 延期风险。

系统应主动提示：

```text
本周周报距离计划交付还有1天，仍有2份日报未确认、5条问题缺少标准依据，存在交付风险。
```

#### 25.3.2 素材质量

回答：

```text
检查员提交的素材能不能支撑报告？
```

展示内容：

1. 问题完整率；
2. 照片完整率；
3. 标准依据匹配率；
4. 责任单位完整率；
5. 位置完整率；
6. 退回率。

系统应主动提示：

```text
本周期36条问题中，8条缺少标准依据，4条照片未同步，3条描述不足100字，建议先完善后生成报告。
```

#### 25.3.3 检查员工作质量

回答：

```text
检查员工作质量行不行？
```

评价维度：

1. 任务完成率；
2. 日报按时提交率；
3. 问题完整率；
4. 日报退回次数；
5. 问题被退回次数；
6. 照片缺失率；
7. 标准依据缺失率；
8. 有效问题数量；
9. 报告采用率；
10. 重复修改次数。

固定规则：

```text
不能单纯以发现问题数量评价检查员。
```

更合理的评价应综合：

```text
提交及时性 + 素材完整性 + 问题有效性 + 退回率 + 报告采用率
```

#### 25.3.4 风险问题

回答：

```text
哪些问题需要管理层关注？
```

展示内容：

1. 重大问题；
2. 较大问题；
3. 重复出现问题；
4. 责任单位集中问题；
5. 无标准依据问题；
6. 已进入报告但后续更正的问题。

#### 25.3.5 评审建议

回答：

```text
是否需要评审？
```

触发评审建议的条件：

1. 重大问题数量大于0；
2. 较大问题数量超过阈值；
3. 同一责任单位问题集中；
4. 标准依据缺失率较高；
5. 问题被多次更正；
6. 报告临近交付但素材不完整；
7. 日报退回率异常；
8. 检查覆盖不足。

系统应主动提示：

```text
建议组织内部评审：本周期存在重大问题1条、较大问题5条，且6条问题缺少标准依据。
```

## 26. 标准匹配作为系统核心智能能力

### 26.1 核心痛点

用户最大痛点是：

```text
检查发现的问题如何快速找到对应标准。
```

用户最费时间的地方不是录入问题，而是：

1. 这个问题违反了哪个标准；
2. 应引用哪一条标准条款；
3. 条款怎么表述；
4. 整改建议怎么写才站得住；
5. 报告中的依据能不能让甲方认可。

因此，标准匹配必须作为系统核心智能能力设计。

---

### 26.2 标准匹配原则

固定规则：

```text
机器推荐 + 人工确认。
```

系统负责推荐可能适用的标准条款和整改建议。

用户负责最终确认、调整或手动补充。

系统必须记录：

1. 系统推荐了哪些条款；
2. 用户最终采用了哪些条款；
3. 用户是否修改了系统推荐；
4. 用户是否手动补充依据；
5. 用户是否填写无标准依据说明。

---

### 26.3 标准匹配输入来源

系统不应只根据问题描述匹配标准。

标准匹配应综合：

1. 项目专业；
2. 检查表专业；
3. 检查项内容；
4. 问题描述；
5. 问题分类；
6. 设备类型；
7. 站场/阀室；
8. 责任单位类型；
9. 关键词；
10. 历史相似问题；
11. 用户历史选择记录。

---

### 26.4 V1实现方式

V1不强依赖复杂AI/RAG。

V1采用：

```text
结构化标准库 + 关键词匹配 + 分类匹配 + 历史相似问题复用
```

标准库结构化字段：

1. 标准编号；
2. 标准名称；
3. 专业；
4. 设备类型；
5. 问题分类；
6. 条款编号；
7. 条款内容；
8. 关键词；
9. 适用场景；
10. 典型问题描述；
11. 整改建议模板；
12. 状态。

---

### 26.5 自动推荐

当用户填写或编辑问题时，系统根据：

```text
专业 + 检查项 + 问题分类 + 问题描述关键词 + 历史相似问题
```

自动推荐：

```text
推荐标准条款 Top 5
```

每条推荐应显示：

1. 标准编号；
2. 标准名称；
3. 条款编号；
4. 条款内容摘要；
5. 匹配原因；
6. 命中关键词；
7. 推荐整改建议。

示例：

```text
命中关键词：防腐层破损、露铁、补口
推荐标准：GB/T xxxx 第x.x条
匹配原因：问题描述中包含“防腐层破损”“露铁”，与该条款关键词匹配。
```

---

### 26.6 用户确认

用户可选择：

1. 采用此条款；
2. 查看其他条款；
3. 手动补充依据；
4. 填写无适用标准说明；
5. 稍后完善。

固定规则：

```text
系统推荐不等于最终判定。
用户确认后，才作为正式判定依据。
```

---

### 26.7 历史相似问题复用

每次用户选择标准后，系统记录：

1. 问题分类；
2. 问题关键词；
3. 用户最终选择的标准条款；
4. 是否采用系统推荐；
5. 对应整改建议；
6. 适用专业和设备类型。

后续遇到类似问题时，优先推荐历史采用过的条款。

该能力不依赖复杂AI，也能让系统持续变聪明。

---

### 26.8 不同端的标准匹配定位

#### 安卓端

安卓端标准匹配目标：

```text
快速推荐，快速选择。
```

表现方式：

```text
系统已推荐3条可能依据
[采用第一条] [查看其他] [稍后补充] [手动补充]
```

安卓端不做复杂标准库浏览。

#### Web端普通检查员

Web端普通检查员重点是补齐标准依据。

能力：

1. 我的待补依据问题；
2. 系统推荐标准；
3. 一键采用；
4. 批量处理相似问题；
5. 手动补充依据。

#### Web端组长/报告编制人

组长重点是检查依据是否站得住。

能力：

1. 报告生成前提示标准依据缺失；
2. 报告编辑时展示台账原依据；
3. 展示系统推荐依据；
4. 展示报告采用依据；
5. 展示人工修改痕迹。

#### 管理层

管理层不看每条标准，但要看风险：

1. 标准依据缺失率；
2. 人工补充依据数量；
3. 无标准依据说明数量；
4. 报告中标准依据更正次数。

## 27. 安卓端核心价值：发现高质量问题并固化有效证据

### 27.1 核心结论

安卓端不是简单日报填报工具。

安卓端核心价值是：

```text
辅助检查员在现场发现高质量问题、判断问题性质、固化有效证据、形成可进入周报/月报的高质量问题素材。
```

周报/月报质量大部分取决于现场检查质量。

如果现场没有发现问题、没有发现重要问题，或现场证据无效，后续Web端报告加工没有意义。

---

### 27.2 安卓端重点支持的四件事

安卓端必须围绕四件事设计：

```text
发现问题
判断问题
固化证据
形成高质量素材
```

---

### 27.3 帮助检查员发现问题

安卓端应提供：

1. 检查重点提示；
2. 常见问题提示；
3. 高风险问题提示；
4. 必拍证据提示；
5. 相关标准提示；
6. 历史类似问题参考；
7. 表外问题快捷入口。

进入任务后，系统应提示本次检查重点。

例如：

```text
本次重点检查：
1. 防腐层破损、脱落、鼓包；
2. 补口补伤质量；
3. 管道裸露、锈蚀；
4. 阴保测试桩、标识完整性；
5. 施工记录与现场一致性。
```

每个检查项应提供：

1. 常见不合格表现；
2. 容易漏看的位置；
3. 建议拍摄角度；
4. 相关标准条款；
5. 严重问题提示。

---

### 27.4 表外问题快捷入口

高质量问题不一定都在检查表里。

安卓端必须提供明显入口：

```text
发现表外问题
```

固定规则：

```text
检查员发现任何现场异常，都可以快速记录为表外问题。
```

表外问题可以：

1. 进入日报；
2. 进入台账；
3. 进入周报/月报；
4. 被标准匹配；
5. 被组长确认。

---

### 27.5 帮助检查员判断问题

安卓端应支持快速问题识别。

新增问题时，可以先让用户选择：

```text
问题类型 / 常见问题模板
```

选择后，系统自动带出：

1. 默认问题分类；
2. 推荐标准条款；
3. 推荐严重等级；
4. 推荐整改建议；
5. 建议拍照清单。

严重等级不能只让用户选择“一般/较大/重大”，系统应提供辅助说明，并根据问题类型推荐等级。

---

### 27.6 标准推荐前置到安卓端

标准匹配不应只在Web端做。

安卓端发现问题时，应提示可能适用标准。

表现方式：

```text
系统推荐3条标准依据
[采用] [查看详情] [稍后完善] [手动补充]
```

该能力用于帮助检查员现场判断问题是否站得住。

---

### 27.7 拍照取证是安卓端核心能力

证据不是附件，而是问题成立的关键依据。

每个问题应引导用户拍摄有效证据。

建议证据照片类型：

| 照片类型 | 作用 |
|---|---|
| 定位照 | 证明问题发生在哪个站场、区域、设备附近 |
| 全景照 | 证明现场环境和问题位置关系 |
| 细节照 | 证明问题本体 |
| 对比照 | 证明问题与合格状态差异 |
| 标尺照 | 证明缺陷尺寸、长度、面积 |

系统可提示：

```text
建议补拍：全景照、细节照、标尺照
```

---

### 27.8 拍照自动固化信息

每张正式取证照片必须自动固化：

1. 拍摄时间；
2. 拍摄人员；
3. 项目；
4. 检查任务；
5. 站场/阀室；
6. GPS；
7. 问题编号；
8. 照片类型；
9. 水印。

这些信息不应依赖用户手动填写。

---

### 27.9 照片质量检查

V1可做基础照片质量提示：

1. 是否模糊；
2. 是否过暗；
3. 是否过曝；
4. 是否缺少GPS；
5. 是否缺少水印；
6. 是否上传失败；
7. 是否未关联问题。

系统提示示例：

```text
当前照片可能过暗，建议补拍。
当前照片未获取GPS，是否重试定位？
该问题只有细节照，建议补拍一张全景定位照。
```

---

### 27.10 证据完整度提示

每条问题应显示证据完整度。

示例：

```text
证据完整
缺少全景照
缺少细节照
缺少责任单位
缺少标准依据
照片未同步
GPS缺失
```

---

### 27.11 高质量问题素材

高质量问题素材至少包括：

1. 问题描述；
2. 有效照片；
3. 责任单位；
4. 准确位置；
5. 严重等级；
6. 标准依据；
7. 整改建议；
8. 检查项来源；
9. 时间；
10. 人员；
11. GPS。

安卓端要围绕这些要素做完整度控制。

---

### 27.12 问题卡片

现场检查中，每条问题可显示成卡片。

示例：

```text
问题003：防腐层局部破损，露出金属基体
完整度：缺少标准依据
照片：3张
责任单位：XX施工单位
位置：XX站场 / XX区域
等级：较大
依据：待确认
状态：可保存，不可提交
```

---

### 27.13 提交前质量检查

提交日报前，系统自动生成质量检查结果。

示例：

```text
本次检查发现问题8条
可提交问题6条
需完善问题2条
照片待同步4张
缺少标准依据3条
```

并列出具体问题：

```text
问题003：缺少标准依据
问题005：照片未同步
问题006：描述不足100字
```

固定规则：

```text
保存草稿：允许不完整。
提交日报：必须满足最低完整度。
```

最低完整度包括：

1. 问题描述；
2. 责任单位；
3. 位置；
4. 严重等级；
5. 照片；
6. 标准依据或无依据说明。

是否强制标准依据，可按项目配置。

---

### 27.14 检查覆盖提醒

安卓端不只记录已发现问题，也要提醒避免漏查。

系统应提示：

1. 必查项还有多少未检查；
2. 高风险项是否已检查；
3. 某类检查项是否全部标为不适用；
4. 某区域是否没有任何记录；
5. 某任务是否没有照片；
6. 本任务未发现问题时是否确认现场无异常。

示例：

```text
还有5个必查项未完成。
本任务未发现任何问题，是否确认现场无异常？
HSE类检查项全部标记为不适用，请确认原因。
```

---

### 27.15 历史问题参考

为了帮助检查员发现问题，安卓端可展示历史类似问题。

进入某个项目、站场、专业、设备时，系统提示：

```text
历史常见问题
```

示例：

```text
该类站场历史常见问题：
1. 防腐层破损；
2. 设备标识缺失；
3. 临时用电不规范；
4. 资料记录不完整。
```

V1可先做简单版本：

```text
按专业 + 分类 + 历史台账问题推荐
```

---

### 27.16 渐进式引导原则

安卓端不能一进入就给用户一堆无意义信息。

固定规则：

```text
用户做到哪一步，系统就在那一步提供支持和引导。
```

页面应采用渐进式引导：

1. 任务开始前：提示检查重点、历史常见问题、高风险事项；
2. 检查项查看时：提示常见不合格表现、标准条款、拍照建议；
3. 发现问题时：优先拍照取证，自动固化时间、地点、人员、GPS；
4. 问题填写时：自动带出默认分类、责任单位候选、整改期限、推荐标准；
5. 保存问题后：提示证据完整度和缺失项；
6. 提交日报前：集中做完整性校验和质量检查；
7. 网络异常时：提示离线保存、待同步照片和同步失败原因。

系统主动提示，用户快速确认。

---

### 27.17 不增加用户负担

安卓端不是越复杂越好。

固定原则：

```text
系统主动提示；
用户快速确认；
能自动带出就不让用户填；
能用模板就不用长文本；
能拍照固化就不让用户事后补证据。
```

现场主路径应保持简单：

```text
发现问题
  ↓
拍照
  ↓
系统自动生成问题素材框架
  ↓
用户补充关键字段
  ↓
系统提示缺什么
  ↓
保存
```

## 29. 安卓端现场检查页面进一步简化与问题取证页定版

### 29.1 核心判断

安卓端现场检查页面的设计必须符合真实检查习惯。

真实现场通常不是：

```text
检查员先打开复杂表单
  ↓
按系统表单逐项寻找问题
```

而是：

```text
检查员先在现场发现问题
  ↓
再打开手机取证、记录、判断、保存
```

因此，安卓端不能围绕“填日报表单”设计，而应围绕“发现问题后的取证记录”设计。

固定规则：

```text
安卓端核心不是填日报；
安卓端核心是帮助检查员发现高质量问题、判断问题、固化有效证据、形成可进入报告的问题素材。
```

### 29.2 安卓端主流程

安卓端主流程定为：

```text
今日检查
  ↓
检查中
  ↓
发现问题
  ↓
问题取证页
      ├─ 拍照/补拍
      ├─ 看照片写描述
      ├─ 系统评价证据
      ├─ 推荐标准
      └─ 保存
  ↓
回到检查中
  ↓
问题篮子
  ↓
提交今日检查成果
```

### 29.3 问题取证页是安卓端最核心页面

固定规则：

```text
问题取证页 = 安卓端最核心页面。
```

该页面必须同时承载：

1. 现场照片查看；
2. 问题描述填写；
3. 问题标题填写；
4. 问题分类与严重等级判断；
5. 责任单位与位置选择；
6. 标准推荐与人工确认；
7. 整改建议生成与修改；
8. 证据完整性提示；
9. 保存问题与补拍。

### 29.4 照片和问题描述必须放在同一个核心页面

固定规则：

```text
照片和问题描述不能分散在两个页面。
```

原因：

1. 检查员通常是看着照片回忆现场情况；
2. 描述必须围绕照片证据展开；
3. 照片太小或离开描述区，会导致检查员无法判断照片是否清楚、是否能证明问题；
4. 后续组长复核和报告生产依赖照片与描述的一致性。

页面设计原则：

```text
上方或左侧：大照片预览区；
下方或右侧：问题描述与判断区；
照片与文字始终在同一页面可见。
```

### 29.5 照片预览必须足够大

照片不能只做成小缩略图。

固定规则：

```text
照片预览区域必须足够大，能让检查员判断：
1. 是否清晰；
2. 是否拍到问题主体；
3. 是否能证明责任单位、位置、问题事实；
4. 是否缺少全景、细节、标尺或对比照片。
```

照片区域至少支持：

1. 大图预览；
2. 左右滑动切换；
3. 放大查看；
4. 照片类型标识；
5. 补拍；
6. 重拍；
7. 删除低质量照片；
8. 设置报告候选照片。

### 29.6 一条问题可关联多张照片

固定规则：

```text
一条问题可以关联多张照片。
```

照片建议分为：

| 照片类型 | 含义 | 作用 |
|---|---|---|
| 全景照片 | 展示问题所在现场环境 | 证明位置和场景 |
| 细节照片 | 展示问题本身 | 证明问题事实 |
| 标尺/对比照片 | 展示尺寸、距离、搭接宽度等 | 支撑技术判断 |
| 责任单位/标识照片 | 展示单位、设备位号、作业票等 | 支撑责任归属 |
| 补充照片 | 后续补充说明 | 辅助说明 |

系统应提示：

```text
当前照片证据是否足够；
是否缺少全景；
是否缺少细节；
是否缺少能证明责任单位或位置的照片。
```

### 29.7 系统应在照片区域直接提示证据质量

照片质量提示不能放在提交日报时才提示。

固定规则：

```text
检查员拍完照片后，系统应立即提示照片证据质量。
```

示例：

```text
√ 已有现场全景照片
√ 已有问题细节照片
! 建议补拍责任单位标识
× 当前照片较模糊，建议重拍
× 缺少能体现尺寸/距离的照片
```

V1 可以先采用规则化提示，不强依赖图像 AI。

规则来源包括：

1. 照片数量；
2. 检查员手动标记的照片类型；
3. 是否包含现场拍照；
4. 是否存在补充照片；
5. 是否存在全景/细节组合；
6. 是否满足项目配置的必拍要求。

### 29.8 问题描述围绕照片证据展开

问题描述区不应只是一个空白文本框。

应支持：

1. 问题标题；
2. 详细描述；
3. 描述模板；
4. 语音输入转文字；
5. 系统根据照片、检查项、分类生成描述骨架；
6. 描述完整性提示。

描述引导建议：

```text
请说明：
1. 在哪里发现；
2. 谁的责任；
3. 发现了什么问题；
4. 与标准要求有什么不一致；
5. 可能造成什么影响；
6. 建议怎么整改。
```

### 29.9 安卓端问题取证页建议线框

```text
┌────────────────────────────┐
│ 问题取证                    │
├────────────────────────────┤
│ 照片大图预览区              │
│ [全景图/细节图/补充图]       │
│                            │
│ ← 滑动查看多张照片 →         │

├────────────────────────────┤
│ 证据提示                    │
│ √ 已有全景照片               │
│ ! 建议补拍细节照片           │
│ ! 建议补拍责任单位标识       │
├────────────────────────────┤
│ 问题标题                    │
│ [____________________]      │
│                            │
```

## 30. Web 端报告生产工作台页面布局

### 30.1 页面定位

Web 端报告页面不应按传统“报告管理”设计。

固定命名建议：

```text
报告生产工作台
```

该页面核心不是维护报告列表，而是回答：

```text
这份周报/月报现在能不能交？
不能交，具体卡在哪？
谁去补？
补完后怎么生成、审核、发布？
```

固定规则：

```text
系统先判断报告能不能交；
再引导用户处理缺项；
最后才允许生成、审批、发布。
```

### 30.2 报告生产工作台三层逻辑

页面逻辑分三层：

```text
第一层：交付判断
  这份报告能不能交？

第二层：质量拦截
  哪些日报、问题、照片、依据、描述、责任单位不合格？

第三层：报告生产
  选择问题 → 编辑快照 → 预览报告 → 提交审批 → 发布导出
```

如果一进入页面就是“新建周报、选择问题、编辑正文”，系统就退化为 Word 编辑器。

### 30.3 页面总布局

报告生产工作台采用三栏结构：

```text
┌────────────────────────────────────────────────────────────┐
│ 项目：XXX        报告类型：周报      周期：2025.7.1-7.7       │
│ [重新检测] [生成/更新草稿] [提交审批] [发布导出] [变更报告]     │
├───────────────┬───────────────────────────┬────────────────┤
│ 左：交付状态   │ 中：问题与素材工作区        │ 右：报告预览/质检 │
│               │                           │                │
│ 能否交付       │ 日报                      │ 报告目录         │
│ 缺项数量       │ 问题台账                  │ 问题快照         │
│ 风险等级       │ 照片证据                  │ 质检结果         │
│ 待处理人       │ 标准依据                  │ 审批记录         │
│               │                           │                │
└───────────────┴───────────────────────────┴────────────────┘
```

三栏含义：

```text
左边告诉用户：能不能交；
中间告诉用户：怎么补；
右边告诉用户：交出去长什么样。
```

### 30.4 左侧：交付状态栏

左侧不是普通菜单，而是报告交付体检结果。

示例：

```text
┌────────────────────┐
│ 报告交付状态         │
├────────────────────┤
│ 当前结论：暂不能交付  │
│ 风险等级：中风险      │
│ 预计缺项：12项        │
│ 影响问题：8条         │
│ 影响日报：3份         │
├────────────────────┤
│ 必须处理             │
│ ① 2份日报未确认       │
│ ② 5条问题缺标准依据   │
│ ③ 3条问题照片不足     │
│ ④ 2条描述不足100字    │
├────────────────────┤
│ 建议处理             │
│ ① 1条重大问题建议评审 │
│ ② 张三素材质量偏低    │
│ ③ 某施工单位重复问题多│
└────────────────────┘
```

系统自动检测：

1. 周期内日报是否全部提交、确认；
2. 台账问题是否为有效；
3. 问题描述是否满足要求；
4. 是否有责任单位；
5. 是否有位置；
6. 是否有标准依据或无依据说明；
7. 是否有照片；
8. 照片是否被选入报告快照；
9. 重大问题是否需要内部评审；
10. 报告是否已有审批中版本或已发布版本。

### 30.5 中间：问题与素材工作区

中间区域是组长/项目负责人处理报告素材的主区域。

建议标签：

```text
[待处理] [日报确认] [有效问题] [照片证据] [标准依据] [报告已选问题]
```

待处理列表示例：

```text
┌────────────────────────────────────────────────────────┐
│ 待处理事项                                              │
├────┬──────────┬────────────┬────────┬────────┬────────┤
│等级│ 类型       │ 问题/日报      │ 责任人   │ 影响     │ 操作   │
├────┼──────────┼────────────┼────────┼────────┼────────┤
│高  │ 日报未确认 │ 7月3日日报     │ 李四     │ 阻止生成 │ 去确认 │
│高  │ 缺标准依据 │ 问题-001       │ 张三     │ 阻止发布 │ 补依据 │
│中  │ 照片不足   │ 问题-008       │ 王五     │ 降低质量 │ 补照片 │
│中  │ 描述较弱   │ 问题-012       │ 张三     │ 需优化   │ 编辑   │
└────┴──────────┴────────────┴────────┴────────┴────────┘
```

用户点击某一项，中间区域自动过滤相关问题或日报。

### 30.6 右侧：报告预览与质检栏

右侧不是简单 Word 预览，而是“边编辑边质检”。

```text
┌────────────────────┐
│ 报告预览             │
├────────────────────┤
│ 一、项目概况          │
│ 二、本周检查情况      │
│ 三、问题统计          │
│ 四、典型问题          │
│ 五、工作建议          │
│ 六、下步计划          │
├────────────────────┤
│ 报告质检              │
│ √ 报告周期完整        │
│ √ 已选问题无重复      │
│ × 3条问题缺照片       │
│ × 2条依据未确认       │
│ ! 1条重大问题未评审   │
├────────────────────┤
│ [预览Word]            │
│ [导出草稿]            │
│ [提交审批]            │
└────────────────────┘
```

质检结果分为：

| 类型 | 含义 | 系统动作 |
|---|---|---|
| 阻断项 | 不处理不能提交或发布 | 禁用提交/发布按钮 |
| 强提醒 | 可以提交，但质量有风险 | 弹窗确认并留痕 |
| 建议项 | 不影响流程，但建议优化 | 提示即可 |

### 30.7 报告问题快照编辑页

报告问题编辑必须采用左右对照结构：

```text
┌──────────────────────────────┬──────────────────────────────┐
│ 左：台账原始事实              │ 右：报告正式表述              │
├──────────────────────────────┼──────────────────────────────┤
│ 问题编号：XJ-20250707-001     │ 报告展示序号：问题1            │
│ 检查员：张三                  │                              │
│ 来源日报：7月7日日报           │ 问题标题：                    │
│ 责任单位：安徽省防腐工程总公司 │ [____________________]        │
│ 原始描述：                    │ 正式描述：                    │
│ 现场记录原文……                │ [多行文本框]                  │
│                              │                              │
│ 原始照片：                    │ 报告照片：                    │
│ [全景] [细节] [补充照片]       │ [勾选用于报告的照片]          │
│                              │                              │
│ 原始依据：                    │ 报告依据：                    │
│ DEC-xxx 第4.3条               │ [采用] [更换] [补充说明]       │
│                              │                              │
│ 整改建议：                    │ 报告整改建议：                │
│ 原始建议……                    │ [多行文本框]                  │
└──────────────────────────────┴──────────────────────────────┘
```

固定规则：

```text
报告问题编辑只能保存报告问题快照；
不得覆盖台账原始事实。
```

按钮：

```text
[保存快照] [保存并下一条] [退回检查员补充] [不纳入本报告]
```

## 31. 检查员 Web 端：我的问题完善工作台

### 31.1 页面定位

检查员从 Web 端进入后，第一优先级不是看报告、看统计、看项目列表，而是处理自己需要完善的问题。

固定页面名称：

```text
我的问题完善工作台
```

固定规则：

```text
检查员 Web 端第一入口 = 我的问题完善工作台。
```

### 31.2 核心操作

检查员 Web 端核心操作包括：

1. 编辑问题描述；
2. 判断严重程度；
3. 确认系统推荐标准；
4. 整理照片证据；
5. 补充整改建议；
6. 保存并提交组长复核。

### 31.3 页面线框

```text
┌────────────────────────────────────────────┐
│ 我的问题完善工作台                           │
├────────────────────────────────────────────┤
```

### 31.5 标准推荐交互

标准推荐不能做成普通下拉框。

错误方式：

```text
标准依据：下拉选择
```

正确方式：

```text
系统推荐候选标准
  ↓
检查员查看推荐理由
  ↓
检查员采用 / 不采用 / 手动搜索
  ↓
系统记录人工确认结果
```

推荐区示例：

```text
系统推荐标准

① DEC-OGP-G-AC-006-2020-1 第4.3条
   推荐原因：
   - 问题描述命中关键词：防腐补口、粘弹体胶带、搭接宽度
   - 问题分类：防腐 / 补口
   - 历史相似问题曾引用该条款
   匹配度：高
   [采用] [查看条文] [不相关]

② GB/T xxxx 第5.2条
   推荐原因：
   - 命中关键词：表面处理、除锈等级
   匹配度：中
   [采用] [查看条文] [不相关]

没有合适标准？
[手动搜索标准库] [填写人工依据说明]
```

按钮规则：

| 按钮 | 用户动作 | 系统动作 |
|---|---|---|
| 采用 | 检查员确认标准适用 | 写入问题依据，记录人工确认 |
| 查看条文 | 检查员查看标准原文 | 展示条款内容、适用范围、历史引用 |
| 不相关 | 检查员否定推荐 | 记录负反馈，后续优化推荐 |
| 手动搜索标准库 | 检查员主动查找 | 按标准编号、关键词、专业搜索 |
| 填写人工依据说明 | 没有明确标准 | 保存说明，供组长审核 |

固定规则：

```text
标准依据采用：系统推荐 → 检查员决策 → 组长复核 → 全程留痕。
```

### 31.6 严重程度判断

严重程度不能只靠用户随意选择。

页面应显示系统建议：

```text
严重程度判断

系统建议：较大
建议原因：
- 该问题涉及施工质量关键工序
- 历史同类问题通常定为“较大”
- 推荐整改期限：3天

请选择：
[一般] [较大] [重大]

用户选择后：
请填写判断理由：
[________________________]
```

固定规则：

```text
系统给建议；
检查员做决策；
组长做复核；
系统记录判断过程。
```

## 32. 标准推荐后端能力待展开

### 32.1 当前先固定设计原则

标准推荐不是前端假功能，必须有后端推荐能力支撑。

固定原则：

```text
系统推荐，用户决策，系统留痕。
```

不能变成：

```text
系统自动填死，用户不知道为什么；
或者用户完全手动查标准，系统没有智能支持。
```

### 32.2 后端推荐能力后续必须单独设计

后续讨论后端时，至少要设计：

输入：

1. 问题标题；
2. 问题描述；
3. 检查项；
4. 专业；
5. 问题分类；
6. 设备类型；
7. 位置；
8. 历史相似问题；
9. 已上传照片标签/人工标注，V1 可选。

处理：

1. 关键词匹配；
2. 分类匹配；
3. 检查项关联标准匹配；
4. 历史相似问题复用；
5. 标准条款权重排序；
6. 人工确认与负反馈回收。

输出：

1. 推荐标准列表；
2. 匹配度；
3. 推荐原因；
4. 条款原文；
5. 历史引用案例；
6. 是否需要人工确认。

## 33. 组长端：日报确认与问题复核

### 33.1 页面定位

组长端核心页面命名为：

```text
日报确认与问题复核
```

该页面不是普通日报审批页，而是质量闸口。

固定规则：

```text
日报确认与问题复核 = 待确认台账问题转为有效台账问题的质量闸口。
```

组长真正要做三件事：

1. 判断这份日报能不能确认；
2. 判断日报里的问题能不能进入有效台账；
3. 判断这些问题后续能不能支撑周报/月报。

### 33.2 页面在主流程中的位置

```text
检查员提交日报
  ↓
系统生成待确认台账问题
  ↓
组长进入“日报确认与问题复核”
  ↓
逐条复核问题质量
  ↓
通过 / 退回 / 作废 / 调整
  ↓
日报确认
  ↓
台账问题变为有效
  ↓
周报/月报可选择
```

### 33.3 页面三栏结构

页面采用三栏结构：

```text
┌────────────────────────────────────────────────────────────┐
│ 日报确认与问题复核                                          │
├────────────────────────────────────────────────────────────┤
│ 项目：XXX        日期：2025-07-07        检查员：张三          │
│ 检查任务：防腐检查、HSE检查       状态：已提交，待组长确认      │
├────────────────────────────────────────────────────────────┤
│ 系统结论：暂不建议确认                                      │
│ 阻断项：3项    强提醒：4项    建议优化：6项                    │
│                                                            │
│ 阻断项：                                                    │
│ ① 问题001 缺标准依据                                        │
│ ② 问题003 责任单位为空                                      │
│ ③ 问题006 照片不能证明问题                                  │
├───────────────┬───────────────────────────┬────────────────┤
│ 左：日报概览   │ 中：问题复核列表            │ 右：问题详情/操作 │
└───────────────┴───────────────────────────┴────────────────┘
```

### 33.4 系统先给确认建议

组长进入页面后，系统应先给出结论：

```text
这份日报是否建议确认；
不建议确认的原因是什么；
阻断项、强提醒、建议优化项分别是什么。
```

系统不能替组长决定通过，但必须替组长发现风险。

### 33.5 左侧：日报概览

左侧只放组长判断需要的信息：

```text
┌────────────────────┐
│ 日报概览             │
├────────────────────┤
│ 检查员：张三          │
│ 检查日期：2025-07-07 │
│ 检查地点：白银站      │

│ 受检单位：4个         │
│ 问题数量：8条         │
│ 现场照片：26张        │
├────────────────────┤
│ 检查项完成情况        │
│ 合格：18             │
│ 有问题：8            │
│ 不适用：5            │
│ 未检查：2            │
├────────────────────┤
│ 系统检查结果          │
│ × 2个未检查项未说明   │
│ × 3条问题缺关键字段   │
│ ! 2条照片质量较弱     │
└────────────────────┘
```

### 33.6 中间：问题复核列表

中间是问题质量清单，不是普通问题表格。

```text
┌────────────────────────────────────────────────────────────┐
│ 问题复核列表                                                │
├────┬────────┬────────────┬────────┬────────┬────────┬──────┤
│结论│ 编号   │ 问题摘要     │ 等级   │ 依据   │ 照片   │ 操作 │
├────┼────────┼────────────┼────────┼────────┼────────┼──────┤
│×   │001     │ 防腐补口不规范│ 较大   │ 缺失   │ 3张    │ 复核 │
│!   │002     │ 作业票填写不全│ 一般   │ 已确认 │ 1张弱  │ 复核 │
│√   │003     │ 灭火器过期    │ 一般   │ 已确认 │ 2张好  │ 复核 │
│×   │004     │ 临边防护缺失  │ 重大   │ 待确认 │ 0张    │ 复核 │
└────┴────────┴────────────┴────────┴────────┴────────┴──────┘
```

每条问题前显示系统质检结论：

```text

! 建议复核
× 不建议通过
```

复核维度至少包括：

1. 问题描述；
2. 责任单位；
3. 位置；
4. 严重等级；
5. 标准依据；
6. 照片证据；
7. 整改建议；
8. 重复问题；
9. 表外问题是否建议加入检查表。

```text
├────────────────────────────────────────────┤
│ 问题描述                                    │
│ 检查员原文：……                              │
│ 系统提示：描述包含现象，但缺少后果说明         │
├────────────────────────────────────────────┤
│ 标准依据                                    │
│ 检查员已选：DEC-xxx 第4.3条                  │
│ 系统推荐：DEC-xxx 第4.5条 匹配度更高          │
│ [采用检查员依据] [改用推荐依据] [手动选择]      │
├────────────────────────────────────────────┤
│ 严重程度                                    │
│ 检查员选择：一般                             │
│ 系统建议：较大                               │
│ 原因：涉及关键施工质量，历史同类多为较大        │
│ [保持一般] [调整为较大] [调整为重大]            │
├────────────────────────────────────────────┤

│ [通过] [退回修改] [组长调整] [作废] [关联重复]  │
└────────────────────────────────────────────┘
```

固定规则：

```text
组长必须看证据做判断，不能脱离照片和标准只看文字审核。
```

### 33.8 组长操作规则

组长操作分为五类：

```text
通过
退回修改
组长调整
作废
关联重复
```

#### 33.8.1 通过

适用场景：

1. 问题事实清楚；
2. 照片能证明；
3. 标准依据准确；
4. 责任单位正确；
5. 严重等级合理；
6. 整改建议可执行。

系统动作：

```text
问题复核状态 = 通过
保留检查员原字段
记录组长、时间、复核意见
```

#### 33.8.2 退回修改

适用场景：

1. 缺照片；
2. 描述不清；
3. 责任单位无法判断；
4. 标准依据不确定；
5. 问题事实需要检查员补充。

必须填写退回原因：

```text
□ 描述不清
□ 照片不能证明问题
□ 缺少全景/细节照片
□ 标准依据不准确
□ 严重等级需重新判断
□ 责任单位需核实
□ 其他：______
```

系统动作：

```text
日报状态 = 已退回
检查任务状态 = 日报退回待修改
相关台账问题状态 = 暂停使用
生成检查员待处理问题
记录退回人、退回时间、退回原因
```

#### 33.8.3 组长调整

适用场景：

```text
问题事实没错；
只是分类、等级、责任单位、依据、整改建议需要微调；
不需要检查员重新补现场证据。
```

可调整字段：

1. 问题分类；
2. 严重等级；
3. 责任单位；
4. 标准依据；
5. 整改建议；
6. 是否纳入报告建议。

系统动作：

```text
保存调整后的台账字段；
记录调整前/调整后；
记录调整人、调整时间、调整原因。
```

边界规则：

```text
组长可以纠偏判断，不能凭空补现场事实。
```

凡是现场事实不清、照片不能证明、证据不足的问题，必须退回检查员补充。

#### 33.8.4 作废

适用场景：

1. 重复问题；
2. 误报问题；
3. 不是本项目问题；
4. 不属于检查范围；
5. 现场事实不成立。

必须填写作废原因：

```text
□ 重复问题
□ 现场事实不成立
□ 非本项目范围
□ 非责任单位问题
□ 已包含在其他问题中
□ 其他：______
```

系统动作：

```text
台账问题状态 = 作废
不进入周报/月报
保留来源日报问题和操作记录
```

#### 33.8.5 关联重复

适用场景：

```text
同一责任单位、同一位置、同一类型问题重复出现，
或与历史未关闭问题高度相似。
```

系统动作：

```text
建立重复/相似问题关联关系；
保留本次问题记录；
记录关联人、关联时间、关联原因；
供后续统计重复发现次数和报告分析使用。
```

### 33.9 日报确认规则

日报确认不能只是一个按钮。

底部按钮建议：

```text
[保存复核进度] [退回日报] [确认日报并生成有效台账] [查看日报预览]
```

点击“确认日报并生成有效台账”时，系统必须二次检查：

1. 是否还有未处理问题；
2. 是否还有阻断项；
3. 是否存在未检查且未说明的检查项；
4. 是否存在待确认标准依据；
5. 是否存在无责任单位问题；
6. 是否存在无照片但项目要求必拍的问题。

如果有阻断项，禁止确认，并提示原因。

确认后：

```text
日报状态 = 已确认 / 已锁定
检查任务状态 = 已完成
通过复核的问题 → 台账状态 = 有效
作废问题 → 台账状态 = 作废
```

### 33.10 留痕规则

以下动作必须留痕：

1. 组长通过问题；
2. 组长退回问题；
3. 组长退回日报；
4. 组长调整严重等级；
5. 组长调整标准依据；
6. 组长调整责任单位；
7. 组长作废问题；
8. 组长关联重复问题；
9. 组长确认日报。

留痕字段至少包括：

1. 操作对象；
2. 操作类型；
3. 操作前内容；
4. 操作后内容；
5. 操作人；
6. 操作时间；
7. 操作原因；
8. 备注。

## 34. Web 端角色视角边界

### 34.1 普通检查员

关注：

1. 问题描述补充；
2. 严重等级判断；
3. 标准依据确认；
4. 照片整理；
5. 退回修改；
6. 保存提交。

不应关注：

1. 报告生产全流程；
2. 管理统计；
3. 报告发布；
4. 其他检查员问题治理。

### 34.2 组长/项目负责人

关注：

1. 日报确认；
2. 问题质量复核；
3. 有效台账治理；
4. 周报/月报生产；
5. 审核发布；
6. 报告变更。

### 34.3 管理层

关注：

1. 项目是否受控；
2. 报告是否能按时交付；
3. 是否有重大风险；
4. 检查员工作质量是否异常；
5. 是否需要组织内部评审。

管理层页面不应堆日报列表和问题明细，而应形成项目质量与交付风险看板。

## 35. 问题台账定位修正：V1 简化为项目问题池

### 35.1 修正原因

前一轮曾将问题台账设计为“报告前的问题质量治理池”。经业务复核，V1 不宜把问题台账做重。

固定修正为：

```text
问题台账 / 问题池不是复杂治理中心，而是已确认日报问题的项目级汇总池。
```

页面面向用户时建议命名为：

```text
项目问题池
```

后台对象仍可继续使用 `IssueLedger` 或类似命名，但前端不要引导用户理解为复杂“治理台账”。

### 35.2 日报与问题池的关系

日报和问题池会有部分字段重叠，但业务视角不同。

| 对象 | 业务视角 | 核心问题 |
|---|---|---|
| 日报 | 某检查员某一天现场检查成果 | 这份日报能不能确认 |
| 项目问题池 | 某项目下所有有效问题集合 | 哪些问题可以被报告引用 |
| 周报/月报 | 对甲方交付的正式报告 | 这份报告能不能交付 |

固定规则：

```text
日报负责收集现场问题。
组长确认日报后，日报中的有效问题进入项目问题池。
项目问题池是周报、月报统一的问题来源。
```

### 35.3 项目问题池 V1 能力边界

V1 项目问题池只保留轻量能力：

1. 查看项目内已确认问题；
2. 按项目、日期、检查员、责任单位、检查地点、专业、严重等级、问题分类筛选；
3. 查看问题来源日报、来源检查任务、来源检查员、来源照片；
4. 显示问题是否已被周报、月报引用；
5. 作为周报、月报自动筛选和人工选题的数据来源；
6. 保留轻量作废能力；
7. 可选保留重复问题关联能力。

V1 暂不做：

1. 复杂问题治理流程；
2. 复杂评审流程；
3. 台账质量评分体系；
4. 独立整改闭环；
5. 自动合并问题；
6. 复杂问题生命周期治理。

## 36. 日报、问题池、周报、月报统一数据链

### 36.1 统一主链

后续固定为：

```text
日报负责收集现场问题
  ↓
日报确认后，问题进入项目问题池
  ↓
周报/月报从项目问题池自动筛选问题
  ↓
生成周报/月报初稿
  ↓
生成报告问题快照
  ↓
编辑正式报告表述
  ↓
审批发布
```

### 36.2 周报来源规则

周报来源固定为：

```text
本周期内，项目问题池中符合筛选条件的有效问题。
```

周报不能直接从以下对象取问题：

1. 日报草稿；
2. 退回中的日报；
3. 现场检查临时记录；
4. 作废问题；
5. 其他报告快照。

### 36.3 月报来源规则

月报来源固定为：

```text
本月或指定周期内，项目问题池中符合筛选条件的有效问题。
```

月报可以参考已发布周报生成摘要、统计或文字提炼，但月报的问题数据源仍然是项目问题池。

固定边界：

```text
周报不是月报的问题来源。
周报只是月报可参考的已发布材料。
```

原因：

1. 避免“日报 → 问题池 → 周报 → 月报”的链路过长；
2. 避免周报未选问题导致月报无法选择；
3. 避免周报变更后月报联动关系复杂；
4. 保持周报、月报生成机制一致；
5. 保持报告问题快照边界清晰。

### 36.4 报告自动筛选条件

周报、月报生成时，系统从项目问题池中按条件自动筛选问题。

常用筛选条件：

| 条件 | 说明 |
|---|---|
| 项目 | 必选 |
| 报告类型 | 周报 / 月报 |
| 日期范围 | 周期开始日期至结束日期 |
| 检查人员 | 全部或指定检查员 |
| 责任单位 | 全部或指定责任单位 |
| 检查地点 | 站场、阀室、区域等 |
| 专业 | 防腐、土建、HSE、无损检测等 |
| 严重等级 | 一般 / 较大 / 重大 |
| 问题分类 | 一级分类、二级分类 |
| 报告引用状态 | 未引用、已进周报、已进月报等 |

用户可以在自动筛选结果基础上人工增减问题，但只能选择项目问题池中的有效问题。

### 36.5 报告生成链路

用户操作：

```text
新建报告
  ↓
选择报告类型：周报 / 月报
  ↓
选择项目
  ↓
选择报告周期
  ↓
设置筛选条件
  ↓
系统从项目问题池自动筛选问题
  ↓
用户确认问题范围
  ↓
系统生成报告草稿和报告问题快照
```

系统动作：

1. 查询项目问题池；
2. 只筛选有效、未作废问题；
3. 排除同一报告内已选问题；
4. 显示每条问题的来源日报和报告引用状态；
5. 生成报告草稿；
6. 为选中问题生成报告问题快照；
7. 初步生成统计数据、问题列表、照片引用和正文框架。

## 37. 问题来源信息与报告引用信息分离

### 37.1 固定来源信息

项目问题池中的每条问题来源固定为日报。

每条问题必须追溯到：

1. 来源日报；
2. 来源日报问题；
3. 来源检查任务；
4. 来源检查员；
5. 来源检查日期；
6. 来源项目检查表；
7. 来源检查项或表外问题；
8. 来源照片。

这类信息属于：

```text
问题来源信息 Source
```

来源信息一旦形成，不因进入周报、月报或报告变更而改变。

### 37.2 动态报告引用信息

周报、月报不是问题来源，而是问题引用方。

一条项目问题池问题可以：

1. 没有进入任何报告；
2. 进入某份周报；
3. 进入某份月报；
4. 同时进入周报和月报；
5. 被多个不同报告版本引用。

这类信息属于：

```text
报告引用信息 Reference / Usage
```

报告引用信息不直接写死在项目问题池问题上，而是通过报告问题快照动态计算。

### 37.3 报告引用状态显示

项目问题池列表和报告选题页面必须显示报告引用状态。

建议状态：

| 状态 | 含义 |
|---|---|
| 未引用 | 尚未进入任何报告 |
| 已进周报 | 已被至少一份周报引用 |
| 已进月报 | 已被至少一份月报引用 |
| 已进已发布报告 | 已被已发布报告引用 |
| 已进当前报告 | 当前报告中已经选择该问题 |

页面示例：

```text
问题001  防腐补口不规范  来源：7月3日日报  引用：第1周周报、7月月报
问题002  灭火器过期      来源：7月4日日报  引用：未引用
问题003  临边防护缺失    来源：7月5日日报  引用：第1周周报
```

点击引用状态，应能查看：

1. 被哪份报告引用；
2. 报告类型；
3. 报告状态；
4. 报告版本；
5. 报告中的问题快照表述；
6. 是否已发布。

### 37.4 同一问题进入多个报告的规则

固定规则：

```text
同一条问题可以进入周报，也可以进入月报。
同一条问题不能在同一份报告中重复出现。
```

月报生成时，系统仍然从项目问题池选题，但必须提示该问题是否已进入过周报。

月报选题可提供筛选项：

1. 包含已进入周报的问题；
2. 仅选择未进入周报的问题；
3. 优先选择已进入周报的重点问题；
4. 全部符合条件问题。

### 37.5 建议字段

项目问题池问题建议保存来源字段：

```text
source_daily_report_id
source_daily_report_issue_id
source_inspection_task_id
source_inspector_id
source_check_date
source_inspection_form_id
source_check_item_id
source_type：表内问题 / 表外问题
```

报告问题快照保存引用关系：

```text
report_id
report_type：周报 / 月报
ledger_issue_id
snapshot_title
snapshot_description
snapshot_standard_basis
snapshot_rectification_suggestion
snapshot_photos
display_order
```

报告引用状态通过 `ReportIssueSnapshot` 和 `Report` 动态统计：

```text
是否进入周报 = 是否存在 report_type = 周报 的快照记录
是否进入月报 = 是否存在 report_type = 月报 的快照记录
进入哪些报告 = 查询快照关联的报告
```

## 38. 报告审批、发布、变更与已发布报告管理

### 38.1 核心原则

V1 审批发布不做复杂流程，但必须守住三条原则：

```text
发布前可以按权限修改。
发布后不能直接修改。
已发布报告如需调整，只能发起变更报告。
```

完整链路：

```text
报告草稿
  ↓
提交审批
  ↓
审批通过
  ↓
发布
  ↓
已发布报告锁定
  ↓
如需修改，发起变更报告
  ↓
生成新版本草稿
  ↓
重新审批发布
```

### 38.2 报告状态

报告状态统一为：

| 状态 | 含义 | 是否可编辑 |
|---|---|---|
| 草稿 | 正在编辑 | 可编辑 |
| 待审批 | 已提交审核 | 不可编辑，除非撤回 |
| 审批退回 | 审核人退回 | 可编辑 |
| 审批通过 | 内部通过，等待发布 | 原则上不可编辑 |
| 已发布 | 已正式交付甲方 | 不可编辑 |
| 已作废 | 报告废止 | 不可编辑 |
| 变更中 | 基于已发布报告生成的新版本草稿 | 可编辑新版本 |

固定规则：

```text
审批通过不等于发布。
发布才代表正式交付。
```

### 38.3 审批配置

V1 支持三种审批模式：

1. 无审批；
2. 一级审批；
3. 两级审批。

配置位置建议：

```text
项目配置 → 报告流程配置
```

配置项包括：

| 配置项 | 说明 |
|---|---|
| 报告类型 | 周报 / 月报 |
| 审批模式 | 无审批 / 一级审批 / 两级审批 |
| 一级审批人 | 角色或指定用户 |
| 二级审批人 | 角色或指定用户 |
| 审批通过后是否允许发布 | 是 / 否 |
| 发布人 | 组长 / 项目负责人 / 指定用户 / 角色 |

审批节点可配置为角色或指定用户。

V1 不做复杂可视化流程设计器。

### 38.4 不同审批模式链路

无审批：

```text
草稿
  ↓
发布
  ↓
已发布
```

一级审批：

```text
草稿
  ↓
提交审批
  ↓
待审批
  ↓
审批通过
  ↓
发布
  ↓
已发布
```

两级审批：

```text
草稿
  ↓
提交一级审批
  ↓
一级通过
  ↓
提交二级审批
  ↓
二级通过
  ↓
发布
  ↓
已发布
```

任一级审批退回：

```text
审批退回
  ↓
报告编辑人修改
  ↓
重新提交审批
```

### 38.5 提交审批前质检

提交审批前必须执行报告质检。

至少检查：

1. 报告是否有问题快照；
2. 所选问题是否全部来自有效项目问题池；
3. 同一问题是否在同一报告中重复；
4. 必填正文是否为空；
5. 问题快照是否缺描述；
6. 问题快照是否缺责任单位；
7. 问题快照是否缺标准依据或无依据说明；
8. 问题快照是否缺照片；
9. 重大问题是否缺评审意见或风险说明；
10. 报告周期、项目、报告类型是否完整。

质检结果分为：

| 类型 | 处理规则 |
|---|---|
| 阻断项 | 未处理不得提交审批或发布 |
| 强提醒 | 可提交，但必须确认并留痕 |
| 建议项 | 不阻断，仅提示优化 |

### 38.6 报告审批页

报告审批页不是只看 Word 文件，而要同时显示：

1. 报告基本信息；
2. 系统质检结论；
3. 阻断项、强提醒、建议项；
4. 报告问题数量；
5. 重大问题数量；
6. 报告预览；
7. 报告问题快照；
8. 来源问题追溯；
9. 审批意见输入框；
10. 通过、退回操作。

审批人可执行：

1. 通过；
2. 退回修改。

审批退回必须填写退回原因。

### 38.7 发布规则

发布时必须固化：

1. 报告基本信息；
2. 报告正文；
3. 报告问题快照；
4. 照片引用快照；
5. 统计数据；
6. 审批记录；
7. 发布人；
8. 发布时间；
9. 导出文件路径；
10. 报告版本号。

发布后：

```text
报告状态 = 已发布
报告正文锁定
报告问题快照锁定
照片引用锁定
审批记录锁定
导出文件记录锁定
```

已发布报告允许：

1. 查看；
2. 导出；
3. 查看审批记录；
4. 查看报告问题快照；
5. 查看来源问题；
6. 发起变更；
7. 作废。

已发布报告禁止：

1. 直接编辑正文；
2. 直接修改问题快照；
3. 直接替换照片；
4. 删除审批记录；
5. 覆盖原导出文件；
6. 原地修改版本。

### 38.8 报告变更规则

已发布报告如需修改，必须发起变更报告。

适用场景：

1. 已发布报告发现文字错误；
2. 问题表述需要调整；
3. 照片选错；
4. 标准依据需要修正；
5. 责任单位表述需要调整；
6. 甲方要求补充说明；
7. 内部复核发现重大遗漏。

用户点击：

```text
发起变更报告
```

系统动作：

1. 复制已发布报告；
2. 复制报告正文；
3. 复制报告问题快照；
4. 复制照片引用；
5. 生成新版本草稿；
6. 版本号递增；
7. 状态置为“变更中”或“草稿”；
8. 记录来源报告 ID；
9. 要求填写变更原因。

示例：

```text
原报告：2025年第1周周报 V1.0 已发布
变更报告：2025年第1周周报 V1.1 草稿
```

变更报告必须重新审批、重新发布，不能绕过审批。

### 38.9 版本与替代关系

新版本发布后，旧版本不直接删除。

旧版本状态可根据项目配置处理：

1. 保留旧版本，标记“已有新版本”；
2. 标记为“已被替代”；
3. 在特殊情况下由用户手动作废。

建议默认：

```text
旧版本保留，并标记为“已被替代”。
新版本标记为“当前有效版本”。
```

### 38.10 已发布报告管理页

页面名称：

```text
已发布报告
```

列表字段建议：

1. 报告名称；
2. 报告类型；
3. 所属项目；
4. 报告周期；
5. 版本号；
6. 状态；
7. 发布时间；
8. 发布人；
9. 是否有新版本；
10. 操作。

操作包括：

1. 查看；
2. 导出；
3. 查看审批记录；
4. 查看问题快照；
5. 查看来源问题；
6. 发起变更；
7. 作废；
8. 查看历史版本。

### 38.11 作废规则

作废不是删除。

适用场景：

1. 报告发错；
2. 周期选错；
3. 项目选错；
4. 内容严重错误；
5. 甲方不认可该版本；
6. 已由其他报告替代且需要废止。

作废必须填写：

1. 作废原因；
2. 作废人；
3. 作废时间；
4. 是否生成替代报告；
5. 替代报告 ID。

作废后：

1. 不能再作为正式有效报告；
2. 保留历史记录；
3. 保留导出文件；
4. 保留审批记录；
5. 保留报告问题快照；
6. 保留来源追溯。

### 38.12 留痕规则

以下动作必须留痕：

1. 生成报告草稿；
2. 修改报告正文；
3. 修改报告问题快照；
4. 增减报告问题；
5. 提交审批；
6. 审批通过；
7. 审批退回；
8. 撤回审批；
9. 发布报告；
10. 导出报告；
11. 发起变更；
12. 发布新版本；
13. 作废报告。

留痕字段至少包括：

1. 操作类型；
2. 操作对象；
3. 操作前状态；
4. 操作后状态；
5. 操作前内容；
6. 操作后内容；
7. 操作人；
8. 操作时间；
9. 操作原因；
10. 审批意见；
11. 变更说明。

# v1.9 补充定版内容：安卓端完整页面链路、提交前校验与离线同步修正版

> 本节用于固化 v1.8 之后已经确认的安卓端现场检查页面、提交前校验、离线同步及“严重等级/标准依据现场不强制确认”的修正结论。后续安卓端原型、接口设计、数据库设计和开发实现均应以本节为准。

## 1. 安卓端总体定位

安卓端不是移动版 Web 后台，也不是普通填表系统。

安卓端的核心定位是：

```text
现场取证记录工具
```

检查员在现场的真实工作顺序通常是：

```text
接到任务
  ↓
到现场
  ↓
开始检查
  ↓
发现问题
  ↓
拍照取证
  ↓
写清问题事实
  ↓
保存到问题篮子
  ↓
提交今日检查成果
```

安卓端设计必须服务于以下目标：

1. 少点页面；
2. 少填字段；
3. 先取证，后补充；
4. 提交前系统拦截关键缺项；
5. 弱网、无网场景不丢数据；
6. 标准依据和严重等级可以推荐，但不在现场强制确认。

## 2. 安卓端页面清单

V1 安卓端主页面压缩为：

```text
1. 今日检查
2. 检查任务详情
3. 检查中
4. 问题取证页
5. 标准推荐确认页
6. 问题篮子
7. 提交今日检查成果
8. 退回问题修改
```

支撑页面包括：

```text
9. 照片大图查看
10. 离线同步状态
```

安卓端页面不能过多，不能把 Web 后台功能搬到手机端。

## 3. 今日检查页

检查员打开 App 后，第一入口为：

```text
今日检查
```

页面展示：

1. 今日任务数量；
2. 待执行任务；
3. 检查中任务；
4. 已退回问题；
5. 同步异常提醒。

检查员主要操作：

```text
开始检查
继续检查
去修改退回问题
```

系统动作：

1. 加载检查任务；
2. 加载项目检查表；
3. 加载项目参与单位；
4. 加载标准库缓存；
5. 启动定位采集；
6. 进入检查中页面。

## 4. 检查任务详情页

任务详情页只显示检查员到现场前必须知道的信息：

1. 项目；
2. 检查专业；
3. 检查地点；
4. 检查表；
5. 计划日期；
6. 组长要求；
7. 离线资料是否已下载。

按钮：

```text
开始检查
下载离线资料
查看检查表
```

如果离线资料未下载，系统提示：

```text
当前任务资料未完整下载，现场无网时可能无法推荐标准。
建议先下载离线资料。
```

但不强制阻断检查员开始检查。

## 5. 检查中页面

检查中页面是现场主页面。

页面必须突出三个入口：

```text
发现问题
问题篮子
检查项列表
```

其中“发现问题”是最高优先级入口。

原因是：现场真实场景中，检查员通常是先发现问题，再打开手机取证和记录，而不是先打开复杂表单逐项填写。

## 6. 问题取证页

问题取证页是安卓端最核心页面。

页面结构：

```text
上半屏：照片大预览
下半屏：问题描述、责任单位、位置、问题来源、可选标准与等级
底部：保存草稿 / 保存到问题篮子
```

页面必须满足：

1. 照片和问题描述在同一个核心页面；
2. 照片预览区域必须足够大；
3. 检查员必须能看着照片写问题描述；
4. 一条问题可关联多张照片；
5. 支持全景照片、细节照片、补充照片；
6. 支持拍照、补拍、重拍、大图查看；
7. 系统提示照片是否清晰、是否能反映问题、是否缺少关键证据。

## 7. 安卓端现场阶段必填项

安卓端现场阶段的核心任务是固化现场事实。

默认必填项为：

```text
1. 照片证据；
2. 问题描述；
3. 责任单位；
4. 位置；
5. 问题来源：表内问题 / 表外问题；
6. 表内问题必须关联检查项。
```

说明：

1. 照片是否必填可由项目配置控制，默认建议必填；
2. 问题描述应尽量清楚描述现场事实；
3. 责任单位来自本次日报实际受检单位列表；
4. 位置包括站场、阀室、具体区域、作业坑编号、设备位号等；
5. 表外问题不修改项目检查表，只作为现场新增问题保存。

## 8. 安卓端现场阶段建议填写项

以下字段在安卓端现场阶段默认不强制：

```text
1. 严重等级；
2. 标准依据；
3. 整改建议；
4. 问题分类。
```

原因：

1. 现场检查员的核心任务是发现问题、拍清证据、写清事实；
2. 标准条款数量多，不能要求检查员在现场准确记忆和选择；
3. 严重等级需要结合标准、项目要求、历史问题和组长判断；
4. 现场强制填写容易导致检查员为了提交而随意选择，反而降低数据质量。

## 9. 严重等级和标准依据的修正规则

固定规则：

```text
安卓端现场阶段不强制检查员确认严重等级和标准依据。
```

系统可以在安卓端推荐严重等级和标准依据，但必须允许检查员选择：

```text
稍后处理
```

页面文案建议：

```text
系统已为你推荐可能适用的标准，可现在确认，也可稍后处理。
```

标准依据区操作：

```text
查看推荐
采用推荐
手动选择
不相关
稍后处理
```

严重等级区操作：

```text
一般
较大
重大
稍后判断
```

## 10. “稍后处理”状态

当检查员现场未确认标准依据或严重等级时，问题仍允许保存和提交。

系统标记：

```text
标准依据状态 = 待确认
严重等级状态 = 待确认
```

后续由以下页面承接：

```text
检查员 Web 端：我的问题完善工作台
组长 Web 端：日报确认与问题复核
```

组长可以：

1. 自己确认标准依据；
2. 自己调整严重等级；
3. 退回检查员补充；
4. 标记无明确标准依据；
5. 要求补充说明。

## 11. 项目配置能力

默认情况下：

```text
标准依据未确认，不阻断日报提交。
严重等级未确认，不阻断日报提交。
```

但系统应预留项目配置：

```text
是否要求提交日报前必须确认标准依据
是否要求提交日报前必须确认严重等级
是否要求提交日报前必须填写整改建议
是否要求提交日报前必须选择问题分类
```

生产环境可根据项目管理要求启用。

## 12. 标准推荐确认页

标准推荐确认页的定位不是让检查员记标准，而是让系统替检查员缩小选择范围。

页面显示：

1. 当前问题摘要；
2. 专业；
3. 分类；
4. 推荐标准列表；
5. 匹配度；
6. 推荐原因；
7. 条款原文查看；
8. 采用、不相关、手动搜索、人工说明、稍后处理。

推荐标准交互规则：

```text
系统推荐
  ↓
检查员决策，可采用、否定、手动搜索或稍后处理
  ↓
Web 端继续确认
  ↓
组长复核
  ↓
全程留痕
```

## 13. 问题篮子

问题篮子是当天所有问题的临时集合，用于提交前自查。

必须显示：

1. 共多少条问题；
2. 可提交多少条；
3. 待完善多少条；
4. 每条问题为什么不能提交或为什么建议完善；
5. 点击后能直接回到对应问题编辑页。

问题篮子不是报告编辑页，也不是台账页。

## 14. 提交今日检查成果

“提交今日检查成果”对应日报提交。

提交前系统必须做完整性校验。

页面显示：

1. 检查任务数量；
2. 问题数量；
3. 照片数量；
4. 受检单位数量；
5. 阻断项；
6. 强提醒；
7. 建议项。

如果存在阻断项，提交按钮禁用。

如果只有强提醒，允许提交，但必须二次确认。

## 15. 提交前校验规则

### 15.1 阻断项

默认阻断项：

```text
1. 项目为空；
2. 检查任务为空；
3. 检查日期为空；
4. 问题描述为空；
5. 责任单位为空；
6. 位置为空；
7. 项目配置要求照片但问题无照片；
8. 表内问题未关联检查项；
9. 未检查检查项未填写原因；
10. 不适用检查项未填写原因。
```

### 15.2 强提醒

默认强提醒：

```text
1. 严重等级未确认；
2. 标准依据未确认；
3. 整改建议未填写；
4. 问题分类未填写；
5. 照片质量较弱；
6. 缺少全景照片；
7. 缺少细节照片；
8. 定位失败但已填写原因；
9. 严重等级与系统建议不一致；
10. 标准依据为人工说明。
```

### 15.3 建议项

默认建议项：

```text
1. 建议补充模板描述；
2. 建议补充整改建议；
3. 建议关联历史相似问题；
4. 建议补充图注；
5. 建议补充责任单位现场佐证照片。
```

## 16. 离线同步规则

现场必须支持弱网、无网。

安卓端所有关键动作必须先本地保存，再异步同步。

关键动作包括：

```text
拍照
填写问题描述
选择责任单位
选择位置
选择严重等级
确认标准依据
保存问题
提交日报
```

本地保存后提示：

```text
已保存到本机，待同步
```

## 17. 客户端唯一编号与同步状态

每条本地数据必须包含：

```text
client_uuid
local_created_at
local_updated_at
sync_status
```

同步状态：

```text
未同步
同步中
已同步
同步失败
冲突待处理
```

## 18. 照片同步规则

照片同步与文字同步分开处理。

规则：

```text
先同步问题文字
再同步照片文件
照片失败可单独重试
照片未同步完成时，组长端应看到提示
```

如果文字已同步、照片未同步，系统显示：

```text
问题已提交，照片待同步，不建议组长确认日报。
```

## 19. 标准库离线缓存

开始检查前，系统应尽量下载：

```text
项目检查表
项目参与单位
常用标准条款
问题分类
历史相似问题摘要，可选
```

离线时：

```text
标准推荐使用本地缓存。
无法在线搜索时提示“当前为离线推荐”。
```

## 20. 冲突处理

V1 不做复杂冲突合并。

只处理三类：

```text
1. 同一问题重复提交；
2. 服务端日报已退回但本地仍在提交；
3. 服务端任务已取消但本地仍在编辑。
```

处理方式：

```text
重复提交：按 client_uuid 幂等处理；
日报已退回：提示用户进入退回修改；
任务已取消：禁止继续提交，保留本地草稿。
```

## 21. 安卓端完整链路

安卓端完整链路固定为：

```text
今日检查
  ↓
检查任务详情
  ↓
检查中
  ↓
发现问题
  ↓
问题取证页
  ↓
可选：标准推荐确认
  ↓
保存到问题篮子
  ↓
问题篮子自查
  ↓
提交今日检查成果
  ↓
系统校验
  ↓
提交日报
  ↓
同步到 Web 端
  ↓
组长日报确认与问题复核
```

## 22. 本节定版规则清单

1. 安卓端不是移动后台，而是现场取证记录工具。
2. 安卓端主页面压缩为今日检查、任务详情、检查中、问题取证页、标准推荐确认页、问题篮子、提交今日检查成果、退回问题修改。
3. 检查员打开 App 后优先看到“今日检查”。
4. 检查中页面必须突出“发现问题”入口。
5. 问题取证页是安卓端核心页面，照片和问题描述必须在同一页。
6. 照片预览区域必须足够大，支持全景、细节、补充照片、重拍、补拍。
7. 安卓端现场阶段不强制确认严重等级和标准依据。
8. 现场阶段核心必填项是照片证据、问题描述、责任单位、位置、问题来源、表内问题关联检查项。
9. 严重等级、标准依据、整改建议、问题分类在安卓端为建议填写项。
10. 系统可以在安卓端推荐标准依据和严重等级，但必须允许检查员选择“稍后处理”。
11. 选择“稍后处理”后，问题标记为标准依据待确认、严重等级待确认。
12. 默认情况下，标准依据未确认、严重等级未确认不阻断日报提交。
13. 项目可配置是否要求提交日报前必须确认标准依据或严重等级。
14. Web端“我的问题完善工作台”和组长端“日报确认与问题复核”负责承接待确认标准和待确认等级。
15. 标准推荐的产品定位不是让检查员记标准，而是让系统先推荐，用户再决策。
16. 问题篮子用于提交前自查，必须显示可提交问题、待完善问题和原因。
17. 提交今日检查成果前必须做完整性校验。
18. 校验分为阻断项、强提醒、建议项。
19. 安卓端所有关键数据必须先本地保存，再异步同步，避免弱网丢失数据。
20. 照片同步与文字同步分开处理；照片未同步完成时，应提示组长不要确认日报。

# v1.10 补充定版内容：标准推荐 V1/V2 边界与可替换架构

> 本节用于固化“标准推荐后端机制 + 标准库字段 + 推荐留痕”的讨论结果。核心修正是：V1 标准推荐只做轻量规则推荐，目标是打通流程；V2 再引入 AI/RAG/图像识别等增强能力。标准推荐能力必须从一开始按“可扩展、可替换”设计，不能写死在日报、问题池、报告等业务模块中。

## 1. 标准推荐的产品定位

标准推荐不是主流程本身，而是主流程中的一个独立推荐服务。

固定原则：

```text
问题信息
  ↓
调用标准推荐服务
  ↓
返回候选标准条款
  ↓
检查员 / 组长确认、否定、手动选择或稍后处理
  ↓
保存确认结果与反馈留痕
```

主业务流程只依赖推荐结果，不依赖具体推荐算法。

也就是说，主流程不关心候选标准来自：

```text
V1 规则匹配
V2 AI/RAG 推荐
V2 图像识别辅助推荐
后续外部标准服务
```

只要返回统一格式的候选标准结果，业务流程即可继续执行。

## 2. V1 标准推荐目标

V1 目标不是“智能识别标准”，而是打通流程。

V1 标准推荐只做轻量、可解释、可人工确认的规则推荐。

V1 实现范围固定为：

1. 根据检查项绑定标准条款进行推荐；
2. 根据专业、问题分类、设备类型进行简单筛选；
3. 根据问题标题、问题描述进行关键词匹配；
4. 返回候选标准条款；
5. 展示推荐原因；
6. 支持用户采用、不相关、手动选择、人工说明、稍后处理；
7. 记录推荐结果与用户反馈。

V1 不实现：

1. AI/RAG 标准匹配；
2. 图像识别后自动推荐标准；
3. 大模型自动判定适用标准；
4. 大模型自动生成正式依据；
5. 自动替用户确认标准；
6. 复杂语义相似问题算法；
7. 将推荐算法作为报告生成的硬依赖。

历史相似问题复用可以预留字段和接口，但不作为 V1 必须完成能力。

## 3. V2 标准推荐目标

V2 的重点是提升识别准确率，减少人工搜索标准的工作量。

V2 可扩展能力包括：

1. AI/RAG 标准条款检索；
2. 语义相似问题匹配；
3. 图片辅助识别；
4. 问题描述自动结构化；
5. 严重等级辅助判断；
6. 历史问题与标准引用模式学习；
7. 根据组长最终确认结果持续优化推荐。

但 V2 增强不能改变主业务流程。

固定规则：

```text
推荐能力可以替换；
主业务流程不能被推荐算法绑定。
```

## 4. 标准推荐服务抽象

后端应抽象独立服务：

```text
StandardRecommendationService
```

统一输入：

| 字段 | 说明 |
|---|---|
| issue_id | 问题 ID，已同步问题使用 |
| client_uuid | 本地问题唯一标识，安卓离线场景使用 |
| project_id | 项目 ID |
| issue_title | 问题标题 |
| issue_description | 问题描述 |
| profession | 专业 |
| issue_category_1 | 一级分类 |
| issue_category_2 | 二级分类 |
| inspection_form_item_id | 来源检查项，表内问题可用 |
| equipment_type | 设备类型，可选 |
| location_type | 位置类型，可选 |
| source_type | 表内问题 / 表外问题 |

统一输出：

| 字段 | 说明 |
|---|---|
| candidate_clauses | 候选标准条款列表 |
| recommendation_score | 推荐分数 |
| confidence_level | 高 / 中 / 低 |
| recommendation_reason | 推荐原因 |
| recommendation_source | 推荐来源 |
| recommendation_provider | 推荐器类型 |
| recommendation_version | 推荐算法版本 |
| requires_manual_confirmation | 是否需要人工确认，固定为是 |

V1 推荐器：

```text
RuleBasedStandardRecommendationProvider
```

V2 可替换推荐器：

```text
AIStandardRecommendationProvider
RAGStandardRecommendationProvider
ImageAssistedStandardRecommendationProvider
ExternalStandardRecommendationProvider
```

业务模块统一调用：

```text
recommendStandards(issueContext)
```

不允许日报模块、问题池模块、报告模块分别实现自己的标准匹配逻辑。

## 5. V1 推荐规则

V1 采用三层轻量规则。

### 5.1 检查项绑定标准

表内问题优先使用来源检查项绑定的标准条款。

```text
来源检查项
  ↓
检查项标准绑定表
  ↓
候选标准条款
```

这是 V1 中最高优先级的推荐来源。

### 5.2 分类匹配

根据以下字段筛选候选条款：

```text
专业
一级分类
二级分类
设备类型
```

分类匹配用于缩小标准条款范围。

### 5.3 关键词匹配

从问题标题、问题描述中提取关键词，与标准条款关键词字段进行匹配。

示例关键词：

```text
补口
搭接宽度
除锈等级
电火花检漏
临时用电
作业票
灭火器
临边防护
```

V1 不要求复杂 NLP，只要求可维护的关键词匹配。

## 6. 推荐分数与推荐原因

V1 推荐分数只用于排序，不作为自动决策依据。

建议评分：

| 来源 | 分值 |
|---|---:|
| 来源检查项直接绑定 | +50 |
| 专业匹配 | +15 |
| 一级分类匹配 | +10 |
| 二级分类匹配 | +10 |
| 设备类型匹配 | +10 |
| 关键词命中 | 每个 +5 |
| 用户曾多次标记不相关 | -20 |

推荐等级：

```text
80 分以上：高
50-79 分：中
50 分以下：低
```

前端必须显示推荐原因，不能只显示匹配度。

示例：

```text
推荐原因：
1. 当前问题来源检查项已绑定该条款；
2. 问题描述命中关键词：补口、搭接宽度；
3. 当前专业为防腐，与条款专业一致。
```

## 9. 标准依据状态

问题上必须维护标准依据状态：

```text
standard_basis_status
```

建议枚举：

| 状态 | 含义 |
|---|---|
| 待推荐 | 问题刚创建，尚未推荐 |
| 已推荐待确认 | 系统已给候选标准，但用户未确认 |
| 已确认 | 用户已采用标准条款 |
| 人工说明 | 用户没有选条款，填写了依据说明 |
| 无明确依据 | 确认没有明确标准条款 |
| 稍后处理 | 现场跳过，后续 Web 端处理 |

固定规则：

1. 标准推荐结果不得自动变成正式依据；
2. 必须经过检查员或组长确认；
3. 组长最终确认结果优先级高于检查员现场选择；
4. 已发布报告中的依据来自报告问题快照，不反写标准推荐记录。

## 10. 严重等级推荐

严重等级推荐同样采用可插拔机制。

V1 可只做简单建议，甚至只预留字段，不作为必须实现能力。

字段建议：

| 字段 | 说明 |
|---|---|
| severity_level | 一般 / 较大 / 重大 |
| severity_status | 待判断 / 系统建议待确认 / 已确认 / 稍后处理 |
| severity_recommendation_provider | 推荐器来源 |
| severity_recommendation_version | 推荐算法版本 |
| severity_confirmed_by | 确认人 |
| severity_confirmed_at | 确认时间 |
| severity_reason | 判断理由 |

固定规则：

1. 安卓现场端可以跳过严重等级判断；
2. Web 端检查员或组长端可以后续确认；
3. 严重等级推荐不得替代人工确认；
4. V2 可结合 AI/RAG、历史问题、图片识别增强等级建议。

## 11. 离线推荐

安卓端离线时使用本地缓存进行轻量推荐。

本地缓存内容：

```text
项目检查表绑定标准
常用标准条款
项目专业相关标准
高频关键词
```

离线推荐必须显示：

```text
当前为离线推荐，结果仅供参考。
```

联网后可以重新推荐。

## 12. 本节定版规则清单

1. 标准推荐在 V1 只做轻量规则推荐，目标是打通流程，不追求高智能。
2. V1 只实现检查项绑定标准推荐、专业/分类匹配、关键词匹配、推荐原因展示、用户确认与反馈留痕。
3. V1 不实现 AI/RAG 标准匹配、图片识别标准推荐、大模型自动判定、自动替用户确认标准、复杂相似问题算法。
4. 标准推荐能力必须封装为独立服务，不允许散落在日报、问题池、报告模块中。
5. 主业务流程只依赖统一推荐接口，不依赖具体推荐算法。
6. 推荐结果必须保存推荐来源、算法版本、输入快照、输出快照、推荐原因和用户反馈。
7. V2 可替换为 AI/RAG/图像识别辅助推荐，但不改变主业务流程。
8. 标准推荐的产品定位是辅助判断，不是替代人工确认。
9. 严重等级推荐同样采用可插拔机制，V1 可只做简单建议或预留字段，V2 再增强。
10. 标准推荐模块必须从一开始按“可扩展、可替换”设计。

## 13. 下一步继续讨论

下一步进入：

```text
字段完整性检查 + 状态机总检查
```

重点检查：

1. 项目、检查表、检查任务、日报、问题池、报告、报告问题快照、照片、标准库、审批记录、操作留痕字段是否完整；
2. 检查任务、日报、问题池问题、报告、审批、照片、标准依据、严重等级等状态是否前后一致；
3. 是否存在字段重复、状态冲突、前端页面无法落地的情况。

## 35. 前端名称与后端对象命名

### 35.1 命名结论

前端面向用户时，统一使用：

```text
项目问题池
```

后端技术对象可以继续使用：

```text
IssueLedger / IssuePool
```

## 36. 标准依据与严重等级状态字段

### 36.1 必须增加状态字段

标准依据和严重等级不能只看字段是否有值。

因为现场阶段允许检查员选择“稍后处理”，后续由 Web 端检查员或组长确认。

日报问题必须维护：

```text
standard_basis_status
severity_status
```

### 36.2 标准依据状态建议

```text
待推荐
已推荐待确认
已确认
人工说明
无明确依据
稍后处理
```

状态含义：

| 状态 | 含义 |
|---|---|
| 待推荐 | 问题刚创建，系统尚未推荐 |
| 已推荐待确认 | 系统已给候选标准，但用户未确认 |
| 已确认 | 用户已确认适用标准条款 |
| 人工说明 | 用户未选择条款，但填写了依据说明 |
| 无明确依据 | 经人工确认没有明确标准条款 |
| 稍后处理 | 现场阶段跳过，后续处理 |

### 36.3 严重等级状态建议

```text
待判断
系统建议待确认
已确认
稍后处理
```

状态含义：

| 状态 | 含义 |
|---|---|
| 待判断 | 尚未判断严重等级 |
| 系统建议待确认 | 系统已给建议，但用户未确认 |
| 已确认 | 用户或组长已确认严重等级 |
| 稍后处理 | 现场阶段跳过，后续处理 |

固定规则：

```text
标准依据和严重等级在安卓现场阶段默认不是强制项。
```

## 37. 项目配置必须承接强制规则

| 配置项 | 说明 |
|---|---|
| 提交日报前是否强制标准依据 | 默认否，可按项目开启 |
| 提交日报前是否强制严重等级 | 默认否，可按项目开启 |

固定规则：

```text
不同项目对现场完整性的要求不同，不允许把强制规则写死在 App 或后端流程中。
```

## 38. 报告引用状态动态计算

### 38.1 固定规则

问题池中的问题不直接写死以下字段：

```text
已进周报
已进月报
进入哪些报告
```

这些信息必须从 `ReportIssueSnapshot` 动态计算。

### 38.2 原因

一条问题可以：

1. 进入周报；
2. 进入月报；
3. 进入多个报告版本；
4. 被变更报告重新引用；
5. 所在报告被作废。

如果把引用状态直接写死在问题池中，报告作废、变更、新版本发布后容易产生不一致。

### 38.3 页面显示规则

问题池列表和报告选题页面应显示：

```text
未引用
已进周报
已进月报
已进已发布报告
已进草稿报告
已进变更报告
```

这些状态均由报告问题快照和报告状态动态推导。

## 39. 照片同步状态对日报确认和报告生产的影响

### 39.1 安卓端允许文字和照片分开同步

安卓端弱网或无网时，允许：

```text
先保存并同步问题文字
后续继续同步照片文件
```

### 39.2 Web 端必须显示照片同步状态

日报确认页必须显示：

```text
该日报是否存在照片未同步问题
哪些问题照片未同步
未同步照片数量
是否影响日报确认
```

报告生产工作台必须显示：

```text
报告所选问题是否存在照片未同步
照片未同步是否影响报告生成和发布
```

### 39.3 默认规则

```text
照片未同步不一定阻断日报提交。
但照片未同步必须强提醒组长，默认不建议确认日报。
```

是否阻断由项目配置决定。

## 68. 页面设计总原则

V1 页面不按数据库表机械拆分，也不按功能菜单堆叠，而按真实用户工作链路组织。

页面分为三类：

```text
主业务页面：每天都用，支撑核心流程
支撑配置页面：项目开始前配置好，平时少用
管理统计页面：管理层看风险、看交付、看质量
```

固定原则：

1. 每个核心页面必须绑定明确业务对象。
2. 每个核心页面必须承接明确业务动作。
3. 不允许出现“看起来有用但不承接主流程”的页面。
4. 安卓端不是移动后台，只做现场检查、取证、保存、提交和退回修改。
5. Web 端承担任务派发、日报确认、问题池、报告生产、审批发布、配置管理和管理统计。
